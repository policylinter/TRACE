# TRACE — подготовка к сдаче

## Что сдаётся

Модульная локальная платформа ИБ: ядро активов, пространств и доступа, импорт и триаж находок, связи с расследованиями и рисками, аудит, политики и экспорт. Это работающий прототип общего ядра и интеграций, а не замена всех специализированных средств защиты. Такое ограничение соответствует исходному заданию.

## Проверить и запустить

**Без ручной настройки целей:** откройте `Start-TRACE-Demo.cmd`. Учебный TRACE работает на http://127.0.0.1:5174/ с отдельной базой `work/local-demo/trace-demo.db`. Он сам создаёт проект `TRACE local test lab`, собственные Python/npm-фикстуры и две локальные цели HTTP baseline. Полная ссылка появляется в консоли и `work/local-demo/ready.json`. Рабочий TRACE на 5173 и его база не заменяются. Ctrl+C останавливает приложение и встроенный HTTP-стенд. Если 5174 или 8878 заняты, запуск откажется, не завершая чужие процессы.

На стенде: **DAST → Проверить HTTP-заголовки** (три наблюдения для варианта без заголовков, ноль для защищённого); **Проверки → Запустить проверку** (путь уже указан в проекте) — реальный Python AST и установленный OSV. Тестовый Python-файл не выполняется. OSV запрашивает публичные координаты npm-зависимости; это не офлайн-анализ. Это учебные цели с настоящим выполнением движков, а не результаты анализа внешнего приложения.

1. В `trace-core` выполните `.venv\Scripts\python.exe tools\check_submission.py` или откройте `Check-Submission.cmd`. Проверка запускает сценарии в отдельных временных базах. Результат и журнал находятся в `work/submission-check.json` и `work/submission-check.log`.
2. Откройте `Start-TRACE.cmd`. Production-интерфейс и API работают вместе на http://127.0.0.1:5173/. Существующая база не заменяется. Если порт занят существующим TRACE, используйте уже работающий сервер.
3. Для переноса нужны оба каталога `trace-core` и `trace-frontend` с `dist`. Python-зависимости описаны в `requirements-runtime.lock`; порядок установки и безопасное создание новой базы — в README. `.venv` и внешние движки зависят от машины и не считаются переносимыми.

## Сценарий показа

1. **Проекты → создать проект.** Дайте понятное имя и адрес собственного репозитория либо `local:submission`.
2. **Проверки → запуск и импорт.** Укажите собственный локальный каталог Python для настоящего встроенного анализа или загрузите внешний JSON. Поддерживаются Trivy, Grype, OSV, Semgrep, ZAP Traditional JSON. Неверный отчёт отвергается без частичного создания проверки.
3. Дождитесь завершения задания. Покажите статус каждого движка: пропуск не означает успешный анализ. Демонстрационный исходный запуск явно помечен.
4. **Находка → чем подтверждается.** Покажите файл/строку AST либо URL и метод из ZAP. Отметьте проверку, назначьте исполнителя, статус и срок. Обновите страницу и убедитесь, что изменения сохранены.
5. Свяжите находку с инцидентом или риском через **Работа команды**. Покажите историю решений и аудит.
6. Экспортируйте VEX. Для непроверенных наблюдений остаётся `under_investigation`; импорт не превращается в доказательство отсутствия проблемы. Для AST и ZAP не выдумывается CVSS.
7. Повторная оценка сохранённой находки не является повторным запуском внешнего сканера. Для проверки исправления выполните новый анализ/импорт.
8. Покажите **Доступ**: роли и изоляцию пространств. Не удаляйте рабочие записи ради демонстрации. После перезапуска сервера проверьте сохранённое состояние.

## DAST: что именно работает

Работает импорт [Traditional JSON ZAP](https://www.zaproxy.org/docs/desktop/addons/report-generation/report-traditional-json/), нормализация, дедупликация, карточка наблюдений, триаж и VEX. TRACE не запрашивает URL из отчёта. Query-параметры, фрагменты, тела запросов и атакующие payload не сохраняются в наблюдениях. URI с учётными данными и экземпляры за пределами сайта отчёта отвергаются.

Также работает собственный HTTP baseline: один GET к явно настроенному loopback HTML и три правила заголовков. Он не заменяет полноценный активный ZAP. Настройка целей и локальный стенд описаны в [37-connected-engines.md](docs/platform/37-connected-engines.md). Не показывайте тестовую JSON-фикстуру как результат настоящего запуска ZAP.

## Что нельзя заявлять на защите

- Полная реализация SIEM/EDR/IAM/PAM/DLP и всех направлений корпоративной ИБ: предусмотрены границы модулей и подключения, а не готовые замены.
- Работа Semgrep на этой машине: CLI установлен, но native engine блокируется доступом Windows к сертификатам. Проверка TLS не отключалась.
- Внешний CI pipeline или полный активный DAST выполнены без соответствующего провайдера/цели и свидетельства запуска. Локальный OSV SCA и CI gate реально проверены; GitLab runner требует подключения.
- AST доказывает эксплуатацию: встроены четыре ограниченных Python-правила; нужен ручной разбор.

Карта возможностей: `docs/platform/03-capabilities.md`. Предыдущий протокол: `FUNCTIONAL-ACCEPTANCE.md`. Актуальные машинные результаты: `work/submission-check.json`.
