# TRACE — локальная версия для запуска и проверки

Перед сдачей: [SUBMISSION.md](SUBMISSION.md). Команда самопроверки — `.venv\Scripts\python.exe tools\check_submission.py` или `Check-Submission.cmd`; временные тестовые базы изолированы от рабочих данных. Отчёты DAST поддерживаются через ZAP Traditional JSON, без обращения к URL отчёта.

Подключённые движки и настройка: [OSV SCA, HTTP baseline и CI gate](docs/platform/37-connected-engines.md). Проверка установленного OSV: `.venv\Scripts\python.exe tools\check_osv.py`. Полный внешний DAST и GitLab runner требуют своих разрешённых целей и настроек.

Для демонстрации без ручной настройки URL откройте `Start-TRACE-Demo.cmd`: отдельный учебный TRACE на 5174, локальный HTTP-стенд и проект для настоящего SAST/SCA. Рабочая база на 5173 не изменяется. Подробности и ограничения — в SUBMISSION.md.

Интерфейс на русском языке. Основное приложение — trace_api/main.py, frontend — соседний каталог trace-frontend. Старые apps/web и apps/agent не являются актуальным запуском.

## Открыть готовую сборку

На Windows дважды нажмите `Start-TRACE.cmd` или выполните из trace-core:

```powershell
.\.venv\Scripts\python.exe run_release.py
```

Откройте http://127.0.0.1:5173/. Это один процесс с API и собранным интерфейсом: Vite, Node, Redis и Docker для этого запуска не нужны. Терминал с сервером должен оставаться открытым; Ctrl+C останавливает сервер. Повторный запуск не завершает чужой процесс на занятом порту: будет понятное сообщение.

Проверка перед запуском без изменения базы:

```powershell
.\.venv\Scripts\python.exe run_release.py --check
```

По умолчанию используется существующая trace_api/trace-platform.db. Она не заменяется демонстрационной копией. Если переносите проект на другую машину, скопируйте оба каталога trace-core и trace-frontend с готовым frontend/dist, установите Python и зависимости:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-runtime.lock
```

Альтернативный frontend задаётся `--frontend C:/path/to/dist`, база — `--database C:/path/to/trace.db`, порт — `--port 5173`. Если базы ещё нет, только явный `--init` разрешает создать новую. Такая база получает явно помеченный демонстрационный запуск; ваши рабочие базы не перезаписываются.

## Сборка frontend при изменении исходников

Из trace-frontend при установленном Node.js:

```powershell
npm ci
npm run build
```

Для разработки: API `.\.venv\Scripts\python.exe run_platform.py` на 8005 и `npm run dev` из frontend на 5173. Не запускайте этот режим одновременно с run_release.py на том же порту. Основной способ демонстрации — готовая сборка с run_release.py.

## Проверочный пользовательский сценарий

1. Проекты → добавить проект → открыть его → «Новая проверка».
2. Открыть запуск и импорт → выбрать настоящий JSON Trivy, Grype, OSV или Semgrep → загрузить. Проверка формы и структуры выполняется до сохранения. Импорт не выдаётся за выполненное TRACE сканирование.
3. Открыть находку → отметить проверку/изменить workflow, ответственного, срок и причину → проверить сохранение после обновления.
4. Экспортировать SBOM/VEX/отчёт. Отсутствие находок и исключение аналитика не доказывают безопасность.
5. Из находки или актива создать связанную задачу, риск или расследование → открыть запись → сохранить решение → проверить историю и обратную ссылку.
6. Реестры активов/источников, inventory, поставки, нормализованные результаты и SAST имеют отдельные формы и историю. Для каждого типа используется свой контракт JSON.

Проектный SAST-запуск принимает только явно разрешённые сервером локальные цели и полный Git commit. Его настройка описана в docs/platform/35-sast-durable-jobs.md. Инструменты, правила и разрешённые цели — отдельные настройки. TRACE не устанавливает фальшивый статус успешного сканирования при отсутствии инструмента.

## Проверки

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

Frontend: `npm run typecheck`, `npm run test:api`, `npm run smoke`. Smoke по умолчанию обращается к работающему TRACE на 5173; другой адрес задаётся переменной TRACE_API. Самопроверка запуска, интеграционные пользовательские сценарии и негативные сценарии импорта находятся в tests/test_release_*.py и tests/test_report_import_validation.py. Все проверки данных выполняются в отдельных временных базах.

## Что требуется настроить отдельно

Локальный режим по умолчанию не требует входа и предназначен для доверенной машины с bind 127.0.0.1. Роли/сессии включаются TRACE_AUTH_ENABLED; не публикуйте локальный режим в сеть. Реальные сканеры, SAST allowlist, AI provider и внешние интеграции требуют своей настройки. Правила вместо недоступной AI-модели помечаются как правила. SIEM/EDR/IAM/PAM/DLP, полноценные DAST и промышленная аттестация не объявляются подключёнными.

Актуальная карта реализации и ограничений: docs/platform/00-current-state.md. Перед сдачей проверьте предусмотренные сценарии и фактические сообщения статусов, а не только число вкладок.

## Проверка установленного Semgrep

Официальный Semgrep изолирован от зависимостей API в `.tools/semgrep`; закреплённая версия указана в `tools/requirements-semgrep.txt`. `Check-Semgrep.cmd` запускает настоящий движок только на сгенерированном тестовом файле и сохраняет `.tools/semgrep-readiness.json`. Автоматическое подключение локальной установки происходит только после успешного теста. Явный `TRACE_SEMGREP_BIN` остаётся настройкой администратора.

На проверенной Windows-машине версия CLI определяется, но native engine завершается с `CertOpenSystemStore returned NULL` до сканирования. Это воспроизводится на минимальном локальном правиле; TLS-проверки и системная защита не отключались. Реальное локальное SAST-сканирование пока не подтверждено; импорт готовых Semgrep JSON и обработка результатов доступны независимо от движка. Ошибка зарегистрирована upstream: https://github.com/semgrep/semgrep/issues/11829.
