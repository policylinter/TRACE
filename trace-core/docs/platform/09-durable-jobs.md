# Этап 2Б.2: постоянные задания, попытки и outbox

Добавлен законченный подэтап постоянного хранения фоновых проверок источников. Состояние больше не зависит от памяти API и Celery result backend. Бизнес-конвейер и прежние HTTP-маршруты сохранены.

## Запись и доставка

`scan_jobs` хранит scope, режим, статусы queued/running/completed/failed, время, приватные параметры и ограниченный публичный результат. `scan_job_outbox` создаётся в той же транзакции: ошибка вставки откатывает и Job. Только после commit диспетчер отправляет ID задания в поток либо Celery. В сообщении брокера больше нет источника, AI-настроек или identity; старые параметры сообщения игнорируются. Источник истины — общая БД API и worker.

Ошибка или неопределённый результат доставки Celery не запускают второе выполнение локально. Outbox остаётся доступным для повторной доставки. При старте API диспетчер предлагает к доставке до 100 queued-заданий, в том числе ранее отправленных, но ещё не захваченных. Ограниченный повтор доставки безопасен за счёт атомарного захвата. Постоянного таймера диспетчеризации пока нет.

Для повторной доставки без перезапуска API оператор может выполнить `python -m trace_api.dispatch_jobs --limit 100` в окружении с нужным TRACE_DATABASE_URL и настройками. Лимит 1–1000. Команда не повторяет running/completed/failed. В локальном режиме она ждёт завершения созданных потоков; в режиме Celery только отправляет сообщения. Счётчик сообщает число предложенных к доставке заданий, а не гарантированно принятых брокером.

## Исполнение и границы гарантий

Worker выполняет условный UPDATE queued → running. Только победитель создаёт `scan_job_attempts` и запускает конвейер. Уникальность attempt.job_id дополнительно запрещает несколько попыток одного Job. Транзакция захвата и создания Attempt едина. После неё свежая сессия заново проверяет текущие права автора и принадлежность проекта пространству — до доступа к исходникам. Для проверки исходников нужна текущая роль admin, как на HTTP-маршруте; понижение до analyst блокирует исполнение. Фоновый rescan использует прежний порог analyst/admin.

Повторная доставка или неизвестный ID возвращают not-claimed и не запускают сканер. Это внутренний результат доставки, а не дополнительный сохранённый статус Job. Завершение Job и Attempt сохраняется одной транзакцией. Доставка и завершение подтверждаются БД, не broker result backend.

Это защита от дублирования исполнения, **не exactly-once результатов**: конвейер сам фиксирует Scan/Finding до записи terminal-state Job. Падение после начала работы оставляет running/Attempt running. Автоматического повторного сканирования, lease, heartbeat и определения погибшего worker пока нет. Такой Job требует операторского расследования; running означает, что выполнение было начато, а не доказанную текущую активность процесса. Не меняйте его на queued прямым SQL ради повтора: сначала нужно проверить уже созданные результаты. Следующий подэтап — безопасное восстановление таких случаев.

Синхронные проверки и фоновый rescan существующей проверки пока не перенесены в Job/Attempt: rescan сохраняет прежний progress API и повторную авторизацию из предыдущего подэтапа. Долговечное хранение здесь покрывает `/api/v1/scans/from-source` с `wait=false`.

## Scope, данные и совместимость

Job связан составным FK с organization/workspace. Список и детали всегда фильтруются одновременно по default-организации и выбранному пространству. Outbox/Attempt и приватные параметры не имеют публичных API. Для Job не используется общий ORM-фильтр доменных таблиц: scope задаётся явно в запросах публичного каталога, worker — доверенный внутренний потребитель. Дополнительные организации всё ещё выключены.

API сохраняет прежние jobId/mode/status, scanId/scanStatus/scanners; добавлены finishedAt и постоянный jobId в деталях. Исходные параметры, sourceMeta и полный текст исключения не возвращаются. Вложенные inline api_key/password/token/secret и URL с userinfo, query или fragment отклоняются до записи с HTTP 422. Фоновые проверки используют серверные настройки интеграций; отдельного secret vault пока нет. Это не DLP для произвольного текста: источник и конфигурация остаются приватными в БД до завершения. В terminal-state params очищаются; для running после сбоя сохраняются для расследования. Автоматической retention-политики Job/Attempt пока нет.

Миграция добавляет три таблицы без изменения старых строк. Данные старого реестра в памяти задним числом восстановить невозможно. API/worker нужно обновлять согласованно, с backup и проверкой копии; старый worker не понимает новый контракт доставки. Redis/Celery должны пользоваться той же БД, что API.

## Проверка

Изолированные тесты проверяют сохранение статуса, приватность параметров, повторную авторизацию, два конкурирующих worker, игнорирование подменённых параметров брокера, единый Job/Outbox rollback, сбой отправки и повтор доставки, очистку terminal params, redaction исключений, составной FK при включённом SQLite foreign_keys и запрет автоматического повтора после имитации падения worker.

Отдельная проверка в трёх Python-процессах: первый дважды мигрировал копию прежнего стенда и создал queued-задание; второй прочитал его и завершил подменённый локальный конвейер; третий прочитал completed и scanStatus=partial. Сохранены 1 проект, 1 проверка, 13 находок, 3 актива, 1 связь. Реальных движков и сторонних целей не запускали.

Новый API также проверен через HTTP на отдельном стенде 8003 с `work/jobs-migration-check.db`: статус фикстуры доступен после смены процесса, health сохраняет прежние counts. Основной API не перезапускался. На тестовой БД 8001 добавлены новые таблицы при проверке запуска; её прежний процесс не заменялся, поскольку порт занят. Перед этим сохранён `work/ui-test-before-durable-jobs.db`. Тестовый 8003 останавливается после проверки; интерфейс в этой итерации не изменён.
