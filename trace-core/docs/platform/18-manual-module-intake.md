# Ручной приём результатов модулей

Добавлены зарегистрированные источники и отдельный журнал импортированных результатов. В UI «Активы и модули» администратор регистрирует источник, включает/выключает приём и импортирует один JSON-документ. Наблюдатели и аналитики читают записи своего пространства. Сервисные аккаунты пока к этому intake не допущены: существующее inventory:write не разрешает импорт результатов.

Это ручной операторский intake, не подключение сканера и не webhook. Направления: appsec, infrastructure, access-data, governance. Принимается только objectType=finding. SecurityEvent, Detection, Incident и Risk требуют иных контрактов и не преобразуются автоматически в находки. Принятые записи не добавляются в прежнюю очередь AppSec Finding и не меняют release gate.

## Контракт trace.intake/1

Обязательные поля: schemaVersion, objectType, sourceId, externalId, assetId, ruleId, title, severity, observedAt и evidence. Описание — до 4000 символов. Title — до 255, rule/external ID — до 128. observedAt требует timezone и приводится к UTC. Evidence — от 1 до 20 записей с label, reference (не более 256 символов) и сообщённым lowercase SHA-256 (64 hex). Неизвестные поля, включая actor/organizationId/workspaceId, отклоняются.

Ссылки — метаданные внешнего отчёта, не скачиваются и не исполняются. Секреты, пароли и персональные данные в этот контракт передавать нельзя; автоматический DLP-фильтр не реализован. SHA-256 evidence сообщён оператором и не проверяется по содержимому файла. Весь импорт сохраняется с verification=not_attested; наличие зарегистрированного источника не является аттестацией его подписи или истинности результата.

Сервер сохраняет организацию и пространство из principal, receivedBy — из его actor, receivedAt — время приёма, sha256 — хеш нормализованного документа. observedAt остаётся заявленным временем исходного наблюдения. Источник и актив должны существовать в том же пространстве. ORM-проверки и FK источника защищают область; внешний ключ на актив дополнен проверкой области в сессии.

Идемпотентность: уникальная пара sourceId/externalId. Повтор точно тех же нормализованных данных возвращает существующую запись (HTTP 200). Новый результат — HTTP 201. Другие данные с тем же ID дают HTTP 409; новая версия отчёта требует нового externalId. Блокировка строки источника сериализует одновременный приём и отключение источника. Выключенный источник отклоняет и новые записи, и повторы.

Журнал module_results неизменяем через API и ORM: изменение/удаление и bulk update/delete отклоняются. Это защита приложения, не WORM-хранилище: прямой оператор SQL может изменить БД. Обновления источника, регистрация и приём аудируются транзакционно. Повтор не создаёт дополнительного события аудита. В аудит приёма попадают только source ID и контрольная сумма, без текста отчёта.

## API

- GET/POST `/api/v1/platform/result-sources` — список/регистрация (до 200 источников в выдаче).
- PUT `/api/v1/platform/result-sources/{id}` с active — включить/выключить ручной приём.
- POST `/api/v1/platform/module-results` — импорт одного документа, только администратор.
- GET `/api/v1/platform/module-results?assetId=...&limit=100&offset=0` — список пространства; limit 1–200, offset от 0. В UI последние 100.

Шаблон UI содержит placeholders для времени и SHA-256, которые должны быть заменены данными реального отчёта. Сам по себе шаблон не проходит проверку. API не запускает сканирование, AI, загрузку evidence или активное реагирование.

## Проверка и продолжение

Шесть новых интеграционных тестов: идемпотентность/конфликт/автор, конкурентный повтор, отключение и область, права и строгая схема, откат при ошибке аудита, неизменяемость и чужие ссылки. Проверяются полный backend suite, TypeScript, production build и API-client smoke. Рабочие находки и настройки сохраняются, тестовые импорты выполняются в изолированных БД.

Не реализованы: аутентификация автоматических коннекторов, подпись webhook/replay window, массовый intake/backpressure, DLQ, occurrence и корреляция между отчётами, evidence blob storage, аттестация и жизненный цикл исправления для импортов. PostgreSQL в живом окружении не проверялся. Следующий шаг — чтение импорта в контексте актива и безопасный lifecycle результата без подмены технического отчёта.
