# Управляемая сверка отсутствующего наблюдения

Добавлены решения аналитика для узла, который есть в выбранном базовом снимке и не попал в выбранный новый снимок. Решение привязано к source/beforeRunId/afterRunId/узлу; оно отделено от фактов инвентаризации и не меняет актив, поля реестра, снимки, актуальность или результаты сканирования. Удаление и запуск повторного сбора не выполняются.

## Допустимый контекст и смысл решения

Используется общая проверка пары со сравнением: снимки должны принадлежать источнику/пространству, быть корректными по контракту и контрольной сумме, идти в хронологическом порядке. Ошибка/нарушение целостности блокирует сверку. Узел должен быть в базе и отсутствовать в цели; для присутствующих в новом снимке узлов этот workflow недоступен.

Для complete-цели это not_in_after, для partial — not_observed_partial. Частичный сбор не устанавливает отсутствие узла. Запись объяснения аналитиком не повышает достоверность снимка и не подтверждает удаление. Появление новых снимков не переносит решение на другую пару автоматически.

Состояния: open («Ожидает сверки»), in_progress («В работе»), needs_observation («Нужно новое наблюдение»), explained («Есть объяснение»). Любая запись/смена состояния требует причины до 4000 символов, включая возврат в open. «Нужно новое наблюдение» — зафиксированная потребность, а не команда запуска сборщика. «Есть объяснение» — ручное решение с основанием, а не независимая проверка факта.

## Хранение, версия и аудит

`inventory_reviews` хранит неизменяемый контекст, SHA-256 выбранных снимков, текущую revision/state и автора/время изменения. Уникальность before_id/after_id/node_id защищает от двух головных записей одной сверки. Контекст и суммы нельзя менять после создания; удаление review запрещено через ORM.

`inventory_review_events` хранит отдельную неизменяемую запись каждого изменения: уникальную пару review_id/revision, before/after состояния, actor и время. История защищена от изменения/удаления, в том числе bulk операций. Связи и источник родителей проверяются в scoped-сессии. Actor определяется сервером, передать его в теле запроса нельзя.

Первое чтение возвращает виртуальную revision=0/open без записи в БД. PUT требует expectedRevision. Изменения сериализуются блокировкой источника, включая гонку первого создания; устаревшая версия — 409. Идентичное сохранение с актуальной версией не создаёт событие и не увеличивает revision. Обновление головы, событие и PlatformAudit коммитятся вместе; ошибка аудита откатывает всё. Само чтение ничего не записывает.

Аддитивно создаются две таблицы; старым данным решения не приписываются. Отключённый для новых импортов источник сохраняет возможность обработки прежних снимков. История в ответе ограничена последними 100 событиями, общий счётчик равен версии сверки.

## API и интерфейс

GET `/api/v1/platform/inventory/sources/{source_id}/reconciliation?before=RUN_ID&after=RUN_ID&externalId=NODE_EXTERNAL_ID` возвращает контекст, вид отсутствующего наблюдения, текущее решение и историю. PUT того же пути принимает beforeRunId, afterRunId, externalId, expectedRevision, status и reason.

Сохранение разрешено admin/analyst своего пространства; viewer читает. Сервисным аккаунтам права не расширяются. Чужие источники/снимки/узлы скрыты; данные и решение связаны с тем же workspace, что и выбранная пара.

В карточке отсутствующего наблюдения раздел «Сверка узла и история решений» загружается по раскрытию. Есть статус, причина, версия/автор/время, история переходов и кнопка обновления со сбросом черновика. При 409 форма сообщает о конфликте; новая версия загружается явно, без скрытого перезаписывания чужого решения. При смене пары/узла компонент получает отдельный контекст.

## Проверка и границы

Пройдены 187 тестов общего набора, TypeScript, сборка и 7 проверок API-клиента. Девять новых тестов проверяют чтение без записей, состояние/историю и неизменность активов, no-op/устаревшую версию/конкуренцию, повторное открытие и независимость пар, partial/error/present-контексты, обязательную причину/права, изоляцию/отключённый источник, атомарный откат, защиту истории/контекста и несогласованную привязку сумм.

На отдельной базе через браузер сохранено «Нужно новое наблюдение» с причиной и версией 1. После параллельной тестовой правки создана версия 2, устаревшее сохранение через UI получило 409, обновление формы показало обе записи истории. Тестовые решения не добавляются в рабочую БД.

Это журнал ручных решений обычной БД с ограничениями ORM, не независимый WORM sink или криптографическая аттестация. Нет автоматического удаления, approval для инфраструктурных действий, расписаний, эскалаций или распределения задач. Следующий практический шаг — подключение согласованного реального источника инфраструктуры через ограниченный read-only коннектор; текущая локальная инвентаризация и сверка не означают подключения CMDB/cloud API.
