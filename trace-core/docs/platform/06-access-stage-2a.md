# Этап 2A — организация и доступ

Продолжение первого этапа, 17 октября 2026. Реализован законченный контур доступа одной организации. Этап 2 целиком **не завершён**: несколько организаций, workspaces, teams и полноценные quotas остаются этапом 2B.

## Что изменено

1. Созданы Organization, Membership, AuthSession и ServiceAccount. Legacy данные Project, Scan, Finding, TriageEvent, Asset, AssetLink и PlatformAudit получают organization_id=default без смены первичных ключей. UI показывает «Основная организация». Заголовок X-Trace-Organization с другим значением всегда получает 403, даже в локальном режиме. Создания дополнительных организаций через API нет.
2. Общая HTTP-проверка охватывает все /api/*, включая прежние чтения, триаж, batch, экспорты, jobs/progress и health. Публичны только auth/status, login, me, logout, preflight; me без действующей сессии не возвращает пользователя. При TRACE_AUTH_ENABLED=1 необходимы активная учётная запись, действующая сессия и активное членство. User.role больше не определяет права запросов — они берутся из Membership.
3. Роли: viewer читает доменные данные и экспортирует отчёты; analyst импортирует отчёты, регистрирует проекты/активы, проводит триаж и повторный анализ; admin дополнительно управляет доступом, настройками AI/политик, запускает проверки источников и удаляет проекты/проверки. Последнего активного администратора нельзя отключить или понизить через API. Конкурирующие изменения сериализуются блокировкой организации (в SQLite — транзакционной записью, в PostgreSQL — FOR UPDATE); отдельный тест двух одновременных понижений сохраняет одного администратора. Изменения членства действуют со следующего запроса.
4. AuthSession хранит SHA-256 токена, user_id, expires_at и revoked в БД. Срок сессии — 8 часов. Перезапуск процесса не теряет сессии. Logout отзывает токен, отключение User или Membership также закрывает доступ. Токены первой версии, которые жили в памяти, требуют нового входа после обновления.
5. Сервисные аккаунты: только при обязательном входе, выдача администратором, токен показывается один раз, в БД только SHA-256, срок 1–90 дней, отзыв без удаления истории. Разрешения перечислены ниже. Аккаунт не может управлять участниками/настройками, выпускать другие токены, запускать источник или AI-анализ. Операционный лимит — 100 активных аккаунтов; это не полноценная система tenant quotas.
6. Автор TriageEvent и PlatformAudit определяется сервером из запроса, а не из поля actor клиента. Исторические записи регистрации получают legacy-unattributed («Автор не установлен»), без выдуманного авторства. Старые поля actor триажа сохраняются как исторические данные. Очередь и rescan передают серверного автора; triggeredBy новых импортов также определяется сервером.
7. API использует OrganizationSession: фильтры ORM SELECT/loader и bulk UPDATE/DELETE по organization_id, запрет чужого ownership и проверка ссылок при flush. Это защита приложения; raw SQL доверенного оператора и прямой доступ к БД не превращаются в tenant boundary. Тестовые чужие строки не видны через списки, advisory joins, detail, экспорты и progress. Перед async rescan проверяется существование доступного scan; пустой проект не получает demo fallback.
8. Защищено удаление проекта с зарегистрированным активом: 409 до изменения данных. Доступ к inventory detail сервисом без scopes на scans/findings больше не выдаёт проектные результаты. Обзор доступности интеграций для неадминистратора исключает detail/топологию/внутренние URL.

## Разрешения сервиса

| Scope | Доступ |
|---|---|
| inventory:read | Реестр/детали активов и каталог модулей; результаты проекта скрыты без дополнительных scopes |
| inventory:write | Регистрация активов и направленных связей |
| findings:read | Прямое чтение находки |
| findings:triage | Review/suppress/unsuppress/workflow и batch; не AI-анализ |
| scans:read | Список/детали проверок, сохранённые результаты, SBOM/reachability/compliance/VEX/progress |
| scans:import | POST /scans с отчётами; только при явном существующем projectId |
| gate:read | Оценка политики/CI gate по сохранённым данным |

Разрешения на сохранённые отчёты предполагают доступ к содержащимся в них сведениям о находках. Это не field-level security. Неизвестный маршрут для сервисного аккаунта запрещён по умолчанию.

## Режимы и совместимость

* AUTH_ENABLED=0 без ADMIN_TOKEN сохраняет прежний локальный режим. Он явно обозначен в UI; персональные ограничения в нём не действуют. Новые сервисные токены в нём не выдаются.
* AUTH_ENABLED=0 с ADMIN_TOKEN теперь защищает **и чтения**, и изменения. Это намеренное устранение обхода. UI прикладывает заголовки к общему транспорту, VEX и выгрузкам. Если токен требуется, появляется соответствующая форма доступа. Старые внешние клиенты чтения должны добавить X-Admin-Token.
* AUTH_ENABLED=1 использует bearer и Membership. Статический токен не обходит персональный вход. Env рабочего экземпляра в этой работе не менялся.

Миграция additive/idempotent через init_db: четыре новые таблицы; ownership-колонки, actor в platform_audit. Legacy пользователи один раз получают членство в default: admin → admin, остальные → analyst (историческое поведение). Маркеры миграции не позволяют повторному старту восстанавливать отозванное членство. Bootstrap-администратор из env учитывается отдельно один раз, в том числе при включении входа после первоначального локального запуска. Тест покрывает свежий bootstrap с SessionLocal.autoflush=False.

Перед обновлением production: резервная копия БД и проверка на копии. Проверены SQLite и повторный init; PostgreSQL execution в этой среде не проверен. Идентификаторы проектов, scans, findings и старый workflow не меняются. Откат кода оставляет additive поля/таблицы, но требует нового входа в старую версию и не должен использоваться для обхода ограничений доступа.

## Интерфейс

Добавлены LoginPage и «Организация и доступ»: контекст организации/роли, участники и изменение членства, сервисные аккаунты/сроки/scopes/отзыв и журнал платформы. UI администратора не доступен наблюдателю. Формы регистрации активов/связей скрыты для viewer; триаж, workflow, AI-анализ, импорт и запуск учитывают роль. Сервер остаётся обязательной проверкой для всех действий.

Logout и 401 очищают приватные данные рабочего состояния; запоздалый 401 от запроса со старым токеном не отзывает новую сессию. Авторизационный токен не добавляется в URL: VEX/compliance скачиваются из ответа, уже полученного с заголовками. API-ответы помечены no-store. Существующий browser token storage пока остаётся localStorage: HttpOnly-сессии, CSP, SSO и защита от XSS — следующие отдельные задачи. В боковой панели убрано неподтверждённое утверждение о GPU-размещении и нулевом egress: это не измеряется TRACE.

## Добавление персонального участника

Доверенный оператор на сервере, с тем же TRACE_DATABASE_URL:

```powershell
python -m trace_api.manage_user analyst-name --role analyst
```

Команда спрашивает новый пароль и подтверждение интерактивно, не принимает секрет в аргументах, требует 12+ символов, создаёт User+Membership+audit атомарно, не перезаписывает существующий аккаунт. Права существующих участников меняются в интерфейсе. Для включения обязательного входа используется прежний TRACE_AUTH_ENABLED=1 и bootstrap env; рабочие учётные данные здесь не создавались.

## Проверка

35 unittest проходят, включая прежние 18 и 17 сценариев доступа. Проверены отсутствие credentials на прежних маршрутах, viewer/analyst/admin, spoofed actor, собственность и чужие ids, экспорт, service scopes/expiry/revoke/no secret echo, сессия/expiry/logout/disabled user, отзыв Membership/last admin, local/static режимы, legacy additive migration и fresh bootstrap, CLI без перезаписи пользователя и сохранение автора обоими путями фоновых заданий. Все данные изолированы.

TypeScript и production Vite build проходят. Сборка использует Vite JS API с configFile:false и теми же React/alias/target, поскольку esbuild CLI в песочнице не разрешает родительский каталог vite.config.ts; исходный config не изменён.

Стенд 8001 перезапущен на прежней тестовой work/ui-test.db после SQLite backup; оба актива, связь и история сохранены. Рабочий процесс 8000 не останавливался. Стенд 8002 использует отдельную work/access-ui.db, rules AI и явно тестовые учётные записи. Через браузер проверены обязательный вход, вход администратора, видимость участников/scopes, выход с очисткой экрана, вход viewer и отсутствие форм изменения активов. Сервисные credentials/права тестировались API-тестами; через браузер новые привилегии не выдавались. После проверки стенд 8002 остановлен, чтобы не оставлять работающую установку с тестовыми учётными данными. Открытый стенд 8001 остаётся локальным режимом с отдельной тестовой БД.

## Следующий этап 2B

Явные Workspace и Team, org-scoped уникальности и составные FK, tenant settings/secret_ref, durable job scope, quotas и adversarial тесты всех экспортов/worker/webhook. Только после этих критериев — создание второй организации. Текущая SQLite-схема пока использует глобальные уникальности external_key/идентификаторов, поэтому включать второй tenant нельзя.

Ещё не реализованы SSO, MFA, rate limiting login, cleanup сессий по retention, audit sink с защитой от администратора БД и проверенная конкурентная миграция нескольких API-процессов. Это не готовый многопользовательский SaaS и не завершение всей ИБ-платформы.
