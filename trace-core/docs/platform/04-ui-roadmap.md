# Интерфейс и поэтапный план

## Информационная архитектура
Целевой верхний уровень: обзор организации; активы и карта связей; безопасность разработки; инфраструктура и облака; мониторинг и инциденты; доступ и данные; риски и соответствие; интеграции; администрирование.

Первый этап: группа «Платформа» → Активы и модули, Проекты; «Безопасность разработки» → прежние обзор, находки, зависимости, проверки, отчёты; «Управление» → существующие база уязвимостей и настройки интеграций/AI. Остальные направления представлены честными planned-строками каталога. Обзор сейчас относится к выбранной проверке, его нельзя называть обзором организации. Будущий обзор организации строится по реальным coverage/ownership/SLA с указанием периода и знаменателя.

Переход: актив → связь с основанием → проверки проекта → находка → доказательства/действия в существующем detail → новая проверка. Карта пока представлена направленными строками; визуальный граф появится при необходимости исследовать реальную цепочку из нескольких узлов. Таблицы, подписи статусов, клавиатурные формы и адаптивный перенос сохраняют компактность. Нельзя подтверждать безопасность зелёным цветом при пустой очереди или ошибке инструмента.

## Совместимость и эксплуатация первого этапа
`init_db()` регистрирует новые модели до create_all. Старые таблицы не ALTER/UPDATE-ятся этим этапом; существующая миграция проекта остаётся прежней. Реестр пуст до ручной регистрации, seed не копируется в inventory. Данные хранятся в трёх новых таблицах; повторный init не меняет записи. Для отката кода таблицы можно оставить; не удалять их автоматически. Перед production upgrade — backup и restore drill в копии; multiwriter требует PostgreSQL. Удаление проекта, связанного с активом, требует отдельной политики lifecycle (в этом этапе не расширяется).

Проверка: `python -m unittest discover -s tests -v` в trace-core; `node node_modules/typescript/bin/tsc --noEmit` в frontend. Для isolated UI используйте TRACE_DATABASE_URL в отдельный файл и TRACE_PORT/VITE_API_TARGET, не создавайте тестовые активы в пользовательской БД.

Ограничения: ручные активы и связи пока только создаются; редактирование, архивирование и bulk import следующие. Список 100 записей в UI (API до 500 с offset), detail до 25 scans/200 findings/100 audit rows. Находки относятся к последней проверке проекта, а не ко всем соседним узлам. Каталог модулей фиксирует контракты и readiness, не исполняет плагины. Новый API использует admin guard целиком, legacy endpoints сохраняют прежнюю модель доступа. Аудит регистрации содержит время и основание, персональная атрибуция будет в этапе 2.
