# Первый локальный исполнитель SAST

19 октября 2026. Добавлен `tools/run_sast_local.py`: операторский CLI для запуска установленного Semgrep по закреплённому commit локального Git-репозитория. Это подготовленный исполнитель, ещё не новый Job kind/веб-запуск. В рабочем окружении Semgrep не обнаружен и не устанавливался; успешного реального Semgrep-анализа на этом этапе нет. Проверки исполнителя используют настоящий Git и явно тестовый процесс сканера.

## Команда и входная область

Из корня trace-core:

```powershell
.\.venv\Scripts\python.exe tools/run_sast_local.py --repo LOCAL_REPOSITORY --commit FULL_COMMIT_HEX --rules TRUSTED_LOCAL_RULES.yaml --source-id APPSEC_SOURCE_ID --asset-id REPOSITORY_ASSET_ID --run-id UNIQUE_RUN_ID --output-dir NEW_OUTPUT_DIRECTORY
```

Замените все placeholders. Требуются доверенный локальный репозиторий, Git с поддержкой --no-lazy-fetch (на стенде 2.54), установленный оператором Semgrep, доверенный локальный файл правил до 64 КиБ, полный lowercase commit 40/64 hex и новый каталог результата. `--scanner` позволяет явно указать одобренный оператором исполняемый файл; никакой путь/команда из веб-запроса или отчёта не запускается. `--timeout` — 1–600 секунд на сканер, по умолчанию 120. Установка бинарников, регистрация источников и выдача прав не выполняются этим CLI.

До запуска сканера валидируются параметры intake, наличие инструментов, commit и дерево. Git разрешает commit через rev-parse и извлекает только объекты его полного дерева через ls-tree/cat-file, без checkout, archive attributes, smudge filters или исполнения проектных скриптов. Git выполняется с запретом lazy fetch/replace refs, системный/глобальный config отключён, исходники не клонируются и не подтягиваются. Незакоммиченные/неотслеживаемые файлы исходного worktree не копируются и не меняются. Git LFS остаётся blob-указателем; submodules/gitlinks и symlink-записи отклоняются, а не загружаются.

Поддерживаются только обычные blob-файлы с безопасными относительными UTF-8 путями. Отклоняются traversal/абсолютные/Windows/UNC пути, неоднозначные регистром имена, `.git` в любом сегменте, завершающие пробелы/точки и Windows device names. Лимит 1000 файлов и 10 МиБ исходных байтов. Записи исполняемого типа экспортируются обычными файлами и не запускаются. Извлечение идёт в новый временный каталог; исходный рабочий репозиторий не используется как cwd Semgrep.

## Выполнение и контроль результата

Вызывается только `semgrep scan` с явным скопированным локальным конфигом, JSON, metrics=off, disable-version-check, no-secrets-validation, jobs=1, timeout=10 и max-memory=512. Это параметры Semgrep, не OS-лимит памяти или гарантия отсутствия сетевого трафика. Бинарник и правила считаются доверенными оператором; пользовательские правила/сканер из произвольного удалённого источника не загружаются.

Окружение процесса сокращено до системных путей/temp и специального пустого home/config. API/CI ключи и SEMGREP_APP_TOKEN не передаются. Python-конфигурация/прокси/Git overrides из родительского окружения не копируются. Shell не используется. stdout и stderr читаются параллельно; на каждый поток установлен предел памяти/объёма. На Git-операцию отведено до 30 секунд, на stdout дерева/объектов — ограниченный размер; это не единый wall-clock budget всего CLI.

Сканеру разрешены exit 0/1 только при валидном JSON-отчёте; код сохраняется в execution receipt и не считается решением release gate. Другие exit, таймаут, слишком большой вывод или невалидный отчёт не создают завершённый manifest. На Windows при остановке вызывается taskkill /T для собственного процесса, затем резервное завершение root PID; на POSIX используется собственная process group. Это не защита от произвольного злонамеренного бинарника или аварии ОС: при гибели supervisor/CLI до cleanup может потребоваться внешний контроль процессов. Работающий через недоверенные бинарники executor требует OS sandbox/job supervision и сетевой изоляции.

После процесса повторно вычисляется fingerprint экспортированных файлов. Любое изменение дерева/байтов останавливает экспорт. Пути активных результатов обязаны существовать в том же snapshot. Это не проверка истинности rule/location или отсутствия пропущенных файлов: сканер и сводка отчёта остаются источником этих сведений. Состояния partial/unknown/no_reported_errors обрабатываются прежним конвертером без повышения доверия или фиктивной чистой находки.

## Выход и приём

В новом каталоге создаются finding-*.json, локальный execution.json и последним — manifest.json. Оригинальный stdout-отчёт, stderr и исходный код не записываются в выходной каталог и не печатаются. execution.json содержит время, exit, SHA-256 правил/отчёта и fingerprint Git snapshot (путь+SHA каждого blob, без самих исходников), число файлов/байтов и commit, разрешённый Git. В receipt хранится сводная сумма fingerprint, а не весь список файлов.

Это локальное неподписанное свидетельство выполнения: `attested=false`, `networkIsolationVerified=false`. Сервер пакетного приёма его ещё не проверяет и не хранит; импортируемый origin.commit остаётся operator-declared. Нельзя подменять им независимую CI/runner attestation. Так как raw отчёт не сохраняется, повторная проверка его SHA требует отдельно безопасно сохранённого исходного файла; автоматического evidence-upload нет.

Для существующего пакетного импорта выбирайте **только manifest.json и finding-*.json**. Execution.json не является intake-файлом и не входит в пакет. При отсутствии manifest экспорт не завершён, даже если отдельные новые файлы появились из-за ошибки записи; их нельзя импортировать как готовую доставку. Существующие каталоги не перезаписываются. Сам CLI ничего не импортирует и не пишет в БД TRACE.

Exit CLI 0 означает готовый экспорт со сводкой no_reported_errors, 2 — partial/unknown либо отказ выполнения. Ни один код не подтверждает безопасность проекта. Даже успешный процесс может пропустить файлы/правила, а отрицательный результат требует проверки наличия завершённого manifest.

## Проверка и дальнейшее подключение

Пять новых тестов используют изолированный Git fixture с настоящим commit, изменённым worktree и untracked-файлом; тестовый процесс подтверждает чтение committed bytes, отсутствие untracked/секретов окружения и ожидаемые флаги. Полученные файлы проходят BatchInput. Также проверены timeout/stdout/stderr limits, отсутствие инструмента и CLI-отказ без вывода кода, неверный commit, отказ перезаписи, symlink tree, опасные пути и изменение snapshot сканером. Общий прогон: 220 тестов, OK (351,481 с); после финальных уточнений путей и отказов CLI повторно прошли все 5 целевых тестов. TypeScript/build и 7 API-client checks прошли. Рабочие 43 таблицы сохранены, 13 прежних находок проверены через 5173. Semgrep не запускается и не имитируется установленным в рабочем UI.

Существующий JobReceipt жёстко связан с legacy Scan. Подключение SAST как отдельного Job kind требует самостоятельного результата/receipt и восстановления статуса; фиктивная CVE/SCA-проверка ради совместимости не создавалась. Следующий этап — server-configured allowlist целей/правил и новый SAST Job с общими capacity/heartbeat/cancel/permission checks, отдельным receipt и журналом выполнения.

Флаги сверены с [официальной CLI-справкой Semgrep](https://docs.semgrep.dev/cli-reference), ограничения чтения объектов — с [Git](https://git-scm.com/docs/git). Это техническая совместимость контракта; конкретный установленный Semgrep ещё требует реальной проверки на разрешённом локальном проекте.
