# Связи импортированных результатов с повторными наблюдениями

Добавлены ручные связи исходного результата с более поздним отчётом. Они не закрывают workflow, не меняют payload или SHA-256 и не означают, что исправление подтверждено. Оба результата доступны из карточки, связь видна с обеих сторон.

## Условия и история

Связать можно только разные ModuleResult одного рабочего пространства с одинаковыми assetId, sourceId и ruleId. observedAt повторного отчёта должен быть строго позже исходного. Это сравнение заявленных времён из отчётов, а не удостоверение runtime-наблюдения. Строго возрастающее время исключает циклы, в том числе при связывании цепочки A → B → C.

У последующего результата может быть только одна активная входящая связь. У исходного возможны несколько последующих наблюдений. Источник блокируется на время изменения; частичный unique index по активному retest_id дополнительно защищает БД. Одновременные разные предшественники дают 201/409. Повтор точно той же активной связи с той же нормализованной причиной возвращает 200 без второго аудита.

Связь хранит original/retest ID, контрольные суммы обоих отчётов, причину, серверные время и actor. Изменение ссылок или удаление через ORM запрещено; bulk update/delete также запрещены. Это защита приложения, не WORM против оператора SQL.

Ошибочную связь можно отозвать с причиной. Запись остаётся в истории с withdrawnAt/By и withdrawalReason; восстановление старой строки не предоставляется. После отзыва можно создать новую связь, не стирая прежнюю. Повтор отзыва с той же причиной идемпотентен; с другой причиной возвращает конфликт. Создание/отзыв и аудит атомарны: сбой аудита откатывает операцию.

## API и UI

- POST `/api/v1/platform/module-results/{id}/retests`: targetResultId и reason (1–4000 символов). Неизвестные поля отклоняются.
- POST `/api/v1/platform/module-retests/{linkId}/withdraw`: reason.
- GET `/api/v1/platform/module-results/{id}` дополнен retests: последние 100 входящих/исходящих связей, включая отозванные.

Аналитик и администратор своего пространства создают и отзывают связи; наблюдатель читает; сервисные аккаунты пока не допущены. Отсутствующие и чужие ID дают 404. Работа со старыми отчётами разрешена и после выключения источника intake.

В карточке импортированного результата появился раздел «Повторные проверки». Кандидаты берутся из текущей страницы (до 100 результатов), дополнительно можно ввести ID. Существует отдельное основание связи и отдельная причина отзыва. Связанный отчёт открывается для просмотра без изменения данных. Обновление связей не сбрасывает черновик workflow и не подменяет expectedRevision его формы.

## Проверка и ограничения

Семь новых тестов покрывают идемпотентность, отображение с обеих сторон, сохранность отчётов и workflow, неверные пары/время/самоссылку, разные активы/источники/правила, конкурентных предшественников, отзыв с историей, права/область, откат аудита и запрет переписывания/удаления ссылок. Полный backend suite — 123 теста; TypeScript, build и 7 проверок API-клиента проходят.

В браузере на изолированном стенде 8007 созданы два тестовых отчёта, сохранена связь, открыт последующий отчёт, затем связь отозвана с причиной. Исходные контрольные суммы и виртуальные состояния new/revision=0 сохранены. Рабочие находки и импорты не изменялись. Основной API обновляется с резервной копией и проверкой сохранности старых строк.

Не реализованы: доказательство идентичности артефакта и окружения, автоматическое подтверждение исправления, объединение результатов разных источников, полный граф цепочки с пагинацией, аттестация evidence и approvals. Здесь связь — заявление команды о сопоставимости двух отчётов. Следующий этап — контекст сборки/артефакта/развёртывания и удостоверенные основания сравнения. PostgreSQL в живом окружении не проверялся.
