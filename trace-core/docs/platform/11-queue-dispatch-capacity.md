# Этап 2Б.2: периодическая доставка и общие лимиты очереди

Добавлен периодический диспетчер outbox и ограничение параллельного исполнения фоновых проверок источников на уровне общей БД. Интерфейс и прежние HTTP-маршруты не менялись; состояние queued и ошибки постановки отображаются существующим экраном проверок.

## Лимиты и атомарный захват

Новая строка `scan_queue_control/default` хранит max_running=2 и max_queued=100. Это общие лимиты установки для включённой default-организации, а не персональные квоты или лимиты отдельных пространств. Они сохраняются между перезапусками и не сбрасываются init.

При постановке Job транзакция сначала обновляет revision строки управления, получая блокировку записи. Затем считает queued и либо сохраняет Job+Outbox, либо возвращает HTTP 429 с Retry-After: 30. Отказ не создаёт Job или Outbox. Это не общая квота на другие сущности: создание Project в существующем HTTP-сценарии предшествует постановке и может уже сохраниться.

При захвате worker та же блокировка сериализует проверку количества running и переход queued → running с созданием Attempt/Heartbeat. Лимит действует одновременно на потоки локального режима и Celery worker, в том числе из разных процессов. При занятой ёмкости статус остаётся queued, попытка не создаётся, конвейер не вызывается. Это не только semaphore одного процесса.

Running с потерянным heartbeat продолжает занимать слот. Освободить его автоматически по тайм-ауту опасно: прежний процесс может продолжать проверку. Восстановление по сохранённому receipt из предыдущего этапа завершает Job и тем самым освобождает слот. Для случая без receipt пока нужна операторская проверка; автоматическая отмена/повтор не добавлены.

## Регулярная доставка

При старте API lifespan запускает отдельный dispatcher-поток. Первый проход выполняется сразу, затем каждые 2 секунды. В shutdown поток получает stop_event и ограниченное ожидание завершения; уже исполняющиеся проверки от этого не отменяются и не получают ложный completed. Диспетчер использует собственные короткие DB-сессии. Ошибка прохода записывается без приватных параметров; следующий проход сохраняется.

Проход выбирает queued по created_at/id с учётом свободной ёмкости. Перед отправкой условный UPDATE Outbox резервирует next_delivery_at на 30 секунд. Поэтому несколько API-процессов не отправляют одно и то же задание в каждом проходе. Резервирование выполняется до Thread.start/send_task. Неопределённая или неуспешная отправка не превращается в локальный второй запуск; после cooldown допускается следующая попытка доставки.

Для локального режима ранее отправленный, но не захваченный queued Job снова доступен после cooldown — например, после падения API между Thread.start и захватом. Для Celery успешно подтверждённое брокером сообщение не отправляется автоматически снова каждый cooldown: иначе при выключенных worker в брокере накапливались бы дубликаты. Потерянное после подтверждения сообщение требует явной операторской повторной доставки, описанной ниже.

Если Celery worker получил сообщение при занятой ёмкости, он возвращает durable Outbox в недоставленное состояние. Позднее подтверждение публикации не может затереть этот возврат: запись подтверждения условна по сроку резервирования, а отказ меняет этот срок. Права автора всё равно заново проверяются только после успешного захвата и до доступа к источникам.

Число предложений к доставке ограничено свободными слотами, однако брокер может содержать ожидающие сообщения до фактического захвата worker. Окончательный лимит тяжёлого исполнения гарантирует транзакционный захват, не предварительная оценка dispatcher. Проверки сообщений/потоки, отклонённые до конвейера, не являются дополнительными запущенными сканерами. Cooldown опирается на согласованные Unix-часы узлов.

## Управление

В окружении с явно выбранным TRACE_DATABASE_URL:

```
python -m trace_api.dispatch_jobs --max-running 2 --max-queued 100 --limit 100
```

Команда сохраняет лимиты и предлагает очередные задания к доставке. Допустимы max-running 1–32, max-queued 1–10000; limit 1–1000 дополнительно ограничивается свободной ёмкостью. Уменьшение лимита не убивает уже работающие проверки: новые ждут, пока количество running станет ниже порога. Изменение конфигурации фиксируется PlatformAudit queue.configured с системным автором system:queue-admin в том же commit. Персональную identity оператора обеспечивает административный shell, отдельного HTTP endpoint настройки нет.

Прежняя команда `python -m trace_api.dispatch_jobs --limit 100` теперь является явной повторной доставкой, включая подтверждённые Celery queued-сообщения, при истёкшем cooldown. Она не забирает running и не повторяет completed/failed. В локальном режиме команда ждёт начатые ей потоки, однако не превращается в постоянно работающий dispatcher; оставшаяся очередь обслуживается запущенным API. Оба пути требуют одной версии API/worker и общей БД.

## Миграция и проверка

Миграция добавляет таблицу управления и `scan_job_outbox.next_delivery_at FLOAT NOT NULL DEFAULT 0`. Старые Job/Attempt/Receipt и бизнес-данные не переписываются. Старые подтверждённые Celery queued-записи не считаются автоматически потерянными после обновления.

На отдельной копии work/queue-process-check.db два init сохранили все прежние столбцы/строки 23 таблиц. В этой копии два отдельных Python-процесса с подменёнными конвейерами проверили max_running=1: второй получил capacity-wait, а после завершения первого выполнился без изменения своего Job ID. Реальные сканеры и сторонние цели не запускались.

Тесты проверяют конкурентную постановку с единственным местом очереди, отсутствие orphan Outbox при 429, Retry-After в реальном HTTP-сценарии TestClient, общий лимит worker, отсутствие новой Attempt при занятой ёмкости, автоматическое опустошение очереди после освобождения слота, восстановление dispatcher после временной ошибки, остановку его потока, совместный cooldown, запрет периодического дублирования Celery ACK и гонку позднего ACK с отказом worker по capacity.

Реальные Redis/Celery и PostgreSQL в этой итерации не поднимались; Celery-публикация проверена подменённым клиентом, PostgreSQL-протокол основан на блокировке строки UPDATE при стандартном READ COMMITTED. Производственных заявлений о throughput и отказоустойчивости брокера пока нет. В рабочие БД и процессы API изменения здесь не применялись; отдельный стенд 8003 от предыдущего этапа не перезапускался.

## Границы и следующий этап

Лимит относится к durable `/api/v1/scans/from-source` с wait=false. Синхронные проверки и прежний фоновый rescan пока не используют этот admission gate. Нет квот на CPU/память/размер источника, приоритетов и справедливого распределения по пространствам, retention, управляемой отмены и автоматического retry исполнявшегося конвейера.

Далее — отмена ожидающих заданий и перенос rescan в общий lifecycle, затем retention и scoped settings/secret_ref. Идемпотентные стадии нужны до безопасного повторения частично выполненного конвейера; дополнительные организации остаются выключены.
Итог: все 75 unittest прошли, включая 9 сценариев диспетчера и лимитов. Межпроцессная проверка и миграция копии БД успешны; git diff --check успешен. Интерфейс не изменялся, новая семантика 429 проверена через HTTP TestClient.
