# Подписанный приём результатов CI

Реализован ограниченный HTTP-приём одного `trace.intake/1` отчёта из заранее зарегистрированного источника. Подпись HMAC-SHA256 подтверждает владение общим ключом доставки. Она не является аттестацией сканера, коммита, SBOM или достоверности находки. Внешние ссылки не загружаются; сканирование, ИИ и задания автоматически не запускаются.

## Настройка

Администратор выбранного пространства читает/меняет `GET/PUT /api/v1/platform/result-sources/{source_id}/webhook`. Тело PUT: `{"enabled":true,"secretRef":"env:CI_KEY"}`. По умолчанию приём выключен. Общий ключ не вводится в UI, не хранится в БД, не возвращается API и не пишется в аудит. В БД сохраняется только ссылка. API разрешает её через отдельную переменную окружения, привязанную к организации, пространству и источнику:

`TRACE_HOOK_<первые 32 hex SHA256("organization:workspace:sourceId") в верхнем регистре>_CI_KEY`

Точное имя показывает API/UI. Оператор задаёт значение в окружении процесса API, перезапускает API и задаёт тот же ключ как защищённый CI secret. UI показывает наличие переменной, состояние источника и число фактически принятых доставок. Включённая настройка без переменной не разрешает приём. Неактивный источник также не принимает отчёты. Сервисные аккаунты не могут управлять настройкой; analyst/viewer получают 403.

## Протокол v1

`POST /api/v1/hooks/results/{source_id}`. Заголовки:

- `X-Trace-Timestamp`: целое число секунд Unix UTC; возраст до 300 секунд, опережение до 30 секунд.
- `X-Trace-Delivery`: стабильный идентификатор доставки, 1–128 ASCII символов `[A-Za-z0-9._-]`.
- `X-Trace-Signature`: `v1=` и 64 строчных hex символа HMAC-SHA256.

Подписываются точные байты сообщения (после delivery ID один LF, затем исходные байты тела):

```text
v1\n{source_id}\n{workspace_id}\n{timestamp}\n{delivery_id}\n{body_bytes}
```

Идентификаторы источника/пространства и заголовки кодируются UTF-8; тело не нормализуется перед проверкой подписи. Максимум 65536 байт. После проверки подписи применяется строгая схема `trace.intake/1`; sourceId документа должен совпадать с URL. Workspace не принимается из тела или заголовка браузера: он определяется по регистрации источника. Метаданные маршрутизации читаются отдельно, затем все операции выполняются scoped-сессией. Actor — `source:<source_id>`.

Единственное исключение из обычной пользовательской авторизации — точный POST указанного формата. Сам обработчик всегда требует действительную подпись, в том числе в локальном режиме. Неизвестный источник, неверная/старая подпись, выключенный приём и отсутствующий ключ возвращают одинаковое 401. Подпись перепроверяется после блокировки источника: изменение настройки и приём сериализованы.

## Повтор, конфликты и транзакция

Журнал `webhook_deliveries` хранит уникальную пару `(source_id, delivery_id)`, SHA256 точных байтов тела и ссылку на результат. Тот же ID/тело с новой действительной подписью возвращает 200/replayed=true. Изменённое тело с прежним ID — 409. Просроченная подпись не принимается даже для повтора. При новом delivery ID с тем же sourceId/externalId действует прежняя дедупликация результата: тот же канонический payload возвращает 200, изменённый — 409.

Результат, необязательный снимок поставки, запись доставки и аудит коммитятся вместе. Сбой откатывает всё. Журнал доставок неизменяем в ORM и bulk update/delete. Ответ содержит только status, deliveryId, resultId, resultSha256 и replayed; чтение остальных результатов этим ключом не разрешается. Ротация переменной окружения требует перезапуска процесса; смена secretRef применяется через настройку. Старые подписи после смены действующего ключа не подходят.

## Отправка из CI

В репозитории есть `tools/send_signed_result.py` на стандартной библиотеке Python:

```powershell
python tools/send_signed_result.py --api-url https://trace.example.internal --source-id SOURCE_ID --workspace-id default --delivery-id PIPELINE_REPORT_ID --secret-env TRACE_CI_KEY report.json
```

TRACE_CI_KEY задаётся CI-хранилищем секретов, не командной строкой. HTTPS обязателен, кроме loopback localhost для тестирования. HTTP-перенаправления запрещены. Скрипт читает максимум 65537 байт, не выводит ключ/тело и при неизвестном исходе предлагает повторить **тот же ID и точные байты файла** с новой подписью. Автоматические ретраи и построение отчёта из произвольного scanner output не добавлены.

## Проверка и границы

Пройдены общий набор 143 тестов, отдельная дополнительная проверка изоляции, TypeScript, сборка и 7 проверок API-клиента. Семь специализированных тестов охватывают подпись, время, лимит, запрет подделанных полей, роли, секрет-ссылки, изоляцию, повторы/конкуренцию, отключение и атомарный откат. На отдельной SQLite-базе реальный sender CLI отправил отчёт и повторил доставку; UI показал ровно одну принятую доставку. Рабочая БД не заполнялась тестовыми результатами.

Это локально проверенный вертикальный этап. Реальный внешний CI, PostgreSQL, публичная публикация API, нагрузочные границы, rate limiting, автоматический retention журнала, Vault/KMS, асимметричная аттестация и хранение файлов доказательств ещё не проверены/не реализованы. Перед сетевым подключением оператор отдельно настраивает HTTPS и доступ; текущая локальная установка остаётся на loopback. Действующие источники автоматически не включаются.
