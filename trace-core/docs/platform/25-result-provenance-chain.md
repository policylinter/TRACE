# Цепочка происхождения импортированного отчёта

Введена запись первичного приёма и read-only представление `trace.provenance/1`. Оно связывает исходный отчёт, способ первого приёма, журнал подписанных доставок и текущую проверку файлов доказательств. Эта цепочка описывает действия API и целостность сохранённых данных; она не аттестует сканер и не подтверждает истинность находки.

## Неизменяемая запись первого приёма

Для новых результатов `module_result_intake_receipts` хранит result_id, область organization/workspace и серверный record: method (manual / signed_hmac), actor, receivedAt, reportSha256, sourceId, assetId, externalId. Для нового отчёта, принятого по HMAC, дополнительно сохраняются ID доставки, SHA-256 точных байтов тела запроса и issuedAt из уже проверенной доставки. Ключ, secretRef и значение подписи в receipt не сохраняются.

Запись создаёт общий сервис импорта только при создании ModuleResult. Она коммитится с отчётом, снимком поставки, аудитом и (при HMAC-приёме) журналом доставки. Ошибка receipt откатывает весь импорт. Повторный ручной/подписанный импорт не создаёт и не меняет receipt. Исходный payload и его контрольная сумма не расширяются полями provenance; прежняя дедупликация остаётся совместимой.

Ручной отчёт, позже повторённый через подписанный канал, сохраняет method=manual. Новая доставка появляется в журнале отдельно. Старым отчётам receipt задним числом не создаётся: API явно возвращает not_recorded. Поле receivedBy, имя источника или наличие поздней HMAC-доставки не используются для догадки о способе первого приёма. Текущее состояние источника показывается отдельно от исторического приёма.

ORM ограничивает чтение пространством, проверяет ссылку на результат и запрещает изменение/удаление receipt, включая bulk операции. Администратор/аналитик/viewer читают представление в своём пространстве; сервисным аккаунтам доступ не расширяется.

## Проверки и API

`GET /api/v1/platform/module-results/{result_id}/provenance?offset=0&limit=20` возвращает:

- report: пересчитанный SHA-256 исходного payload и проверку его sourceId/assetId/externalId против сохранённых связей;
- initialIntake: not_recorded / consistent / integrity_error, сохранённую запись первого приёма и проверку её полей против отчёта; для signed_hmac дополнительно проверяется связь с исходной записью журнала доставки;
- signedDeliveries: общее число, ограниченную страницу записей (максимум 50), ID/время/суммы и проверку связи с отчётом; повтор одного delivery ID не размножает записи;
- evidence: текущую независимую сверку сохранённых байтов доказательств против суммы из отчёта;
- source: текущую регистрацию источника, checkedAt и явное attestation=not_performed.

Для выборки истории добавлен индекс webhook_deliveries.result_id, создаваемый также на существующей таблице (checkfirst). Миграция аддитивная и идемпотентная; прежние строки не меняются. GET не записывает аудит/receipt и не изменяет workflow, release gate или результаты.

В карточке импортированного результата добавлен раскрываемый раздел «Происхождение и проверенные связи». Он отдельно показывает проверки TRACE и факт HMAC-проверки в момент доставки. История подгружается страницами, цепочку можно обновить. SHA-256 тела запроса и канонического отчёта различаются по назначению: снимок поставки добавляется сервером, исходные байты тела не нормализуются перед проверкой HMAC.

## Проверка и границы

Пройдены 161 тест общего набора, TypeScript, сборка и 7 проверок API-клиента. Добавлены 9 тестов первичного manual/signed_hmac приёма, позднего подписанного повтора без повышения доверия, отсутствующего legacy receipt, изоляции/ролей/сервисных аккаунтов, пагинации, неизменяемости, повреждения данных, атомарного отката, чтения без записей и FK. Рабочий интерфейс проверен на отдельной базе с реальным sender CLI и сохранённым файлом доказательства. Тестовые отчёты и ключи в рабочую БД не добавляются.

Receipt и журнал — серверные записи обычной БД, а не независимое WORM-хранилище или криптографически заверенная аттестация. Без сохранённого ключа и исходной подписи здесь невозможно независимо перепроверить исторический HMAC; отображается факт успешной проверки API в момент приёма. Согласованность записей и совпадение сумм не доказывают истинность отчёта. Асимметричная аттестация, доверенные идентичности CI через OIDC, прозрачный журнал и внешняя проверка provenance остаются следующими отдельными задачами.

Следующий этап — первый практический коннектор инфраструктуры с явным источником, временем актуальности и обработкой ошибок; общая цепочка приёма и доказательств уже может использоваться им без создания фиктивных показателей безопасности.
