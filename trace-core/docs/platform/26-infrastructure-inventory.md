# Инфраструктурная инвентаризация и актуальность

Реализован первый пассивный сценарий инфраструктурного модуля: локальный сборщик → JSON-снимок → источник инвентаризации → неизменяемые наблюдения → активы общего реестра. Сетевое обнаружение, сканирование уязвимостей и автоматическое подключение к облакам не выполняются. Статус модуля в UI — «Частично реализовано», с явным описанием границ.

## Локальный сборщик и контракт

`tools/collect_host_inventory.py` использует стандартную библиотеку Python для чтения имени и семейства/версии ОС **только того компьютера, где его запускает оператор**. Нет сетевых запросов, SSH, командного сканирования, чтения секретов или отправки результата. При сбое возвращается статус error с безопасным сообщением без текста исключения.

```powershell
python tools/collect_host_inventory.py --external-id workstation-01 --run-id local-20261018-01 --output report.json
```

external-id — стабильный ID узла, назначенный оператором внутри источника; run-id — уникальный ID конкретного снимка. `--output` создаёт UTF-8 JSON и не перезаписывает существующий файл. Для повторной доставки сохраняют тот же файл/run-id; новый запуск должен получить новый run-id. Без --output JSON печатается в stdout. Сборщик не запускается автоматически из веб-интерфейса.

`trace.inventory/1` содержит schemaVersion, externalRunId, observedAt с часовым поясом, status (complete/partial/error), items и errors. Узел содержит externalId/name, kind server/cloud, необязательные заявленный owner, platform/version/provider/region. Ошибка содержит code (collection_failed/access_denied/limit_reached/invalid_item/unknown) и message. Другие поля запрещены.

Пример структуры:

```json
{
  "schemaVersion": "trace.inventory/1",
  "externalRunId": "export-001",
  "observedAt": "2026-10-18T12:00:00Z",
  "status": "complete",
  "items": [{"externalId": "host-01", "name": "Host 01", "kind": "server", "platform": "Linux"}],
  "errors": []
}
```

Это формат TRACE для ограниченного экспорта инвентаризации; совместимость с произвольным CMDB/Ansible/cloud output не заявляется. Внешний экспорт сначала приводится к этому контракту. Ключи/пароли в документ не включаются.

## API и состояние сбора

`/api/v1/platform/inventory/sources`: GET первых 100 источников, POST регистрации имени/порога freshnessHours (1–720 ч). PUT `/{source_id}` меняет active/freshnessHours с аудитом. GET `/{source_id}?offset=0&limit=100` возвращает текущую настройку, последнюю попытку, страницу узлов с последними наблюдениями и 10 последних снимков. Время checkedAt показывает момент расчёта актуальности.

POST `/{source_id}/snapshots` принимает максимум 256 КиБ/100 узлов/20 ошибок. complete не допускает errors; partial/error требуют описание ошибки; error не допускает items. Повторные externalId внутри снимка запрещены. Время приводится к UTC, опережение более 30 секунд отклоняется. Новый снимок должен быть строго позже последней принятой попытки источника, включая ошибочную; запоздавший снимок не оттеснит более новые данные.

sourceId/externalRunId идентифицируют снимок. Тот же канонический документ возвращает прежнюю запись с 200; изменение документа под тем же ID — 409. Работа сериализуется блокировкой источника. Ошибка аудита или конфликт откатывает снимок, наблюдения и новые активы целиком. Ссылки/типы/число узлов проверяются до сохранения; лимит тела проверяется при чтении потока.

## Идентичности, история и актуальность

Четыре добавочные таблицы: inventory_sources (настройки), inventory_runs (исходный payload, SHA-256, время/actor приёма), inventory_nodes (постоянная связь externalId источника с активом), inventory_observations (сведения узла и время конкретного наблюдения). Run/node/observation неизменяемы через ORM, включая bulk update/delete. Ссылки и рабочее пространство проверяются. Новый актив получает source=inventory и ключ в пространстве имён источника; совпадение с ручным externalKey не объединяет активы. Тип существующего узла нельзя менять молча: требуется новая идентичность.

Наблюдение не перезаписывает имя, owner, проект и связи уже зарегистрированного актива. Заявленный owner остаётся сведением источника; при создании актива ответственный реестра остаётся неназначенным. Новые наблюдения и исходные снимки сохраняют историю изменений сведений. Удаление/автоматическое списание узлов не реализовано: отсутствие в полном или частичном снимке сохраняет прежнее наблюдение, которое со временем устаревает.

current означает, что последнее наблюдение конкретного узла укладывается в настроенный порог **по времени из отчёта**; stale — что порог превышен; unknown — что наблюдения нет. Ошибка/пустой снимок не создаёт наблюдений и не освежает узлы. Последняя попытка сбора показывается отдельно, поэтому свежесть старых данных не скрывает новый сбой. complete относится только к заявленной области сборщика и не доказывает покрытие всей инфраструктуры.

## UI, права и проверка

В «Активах и модулях» добавлена инвентаризация: регистрация/настройка источника, загрузка JSON-файла или текста, история complete/partial/error, последние наблюдения с актуальностью и переходом в общий актив. На узком экране таблица превращается в карточки. В общем реестре источник импорта отличается от ручной регистрации.

Регистрация/настройка/импорт доступны admin, чтение — analyst/viewer своего пространства. Права существующих сервисных аккаунтов не расширены. Полученные данные не создают находки, не подтверждают безопасность и не запускают сканеры/задания.

Пройдены 170 тестов, TypeScript, сборка и 7 проверок API-клиента. Девять новых тестов покрывают дедупликацию, время/контракт/лимиты, роли/изоляцию, ошибку/частичный сбор/пустой снимок, сохранение ручных полей, атомарный откат/конкуренцию, постоянство идентичности, пагинацию и безопасный локальный сборщик. В отдельной базе через браузер импортирован файл реального пассивного локального сборщика с QA-идентичностью, затем тестовый error-снимок: один узел остался current, другой stale, время наблюдений не изменилось из-за ошибки. Тестовые записи не добавлены в рабочую БД.

Ограничения: нет автоматического расписания/удалённого опроса, discovery/cloud API/CMDB коннекторов, глобальной квоты/retention истории, асимметричной аттестации снимка, распределённого большого импорта и проверенного промышленного масштаба. Проверено на локальной SQLite-установке. Следующий этап — сравнение последовательных наблюдений и явное отображение изменений/отсутствия узлов без автоматического удаления и без объявления этого фактом уязвимости.
