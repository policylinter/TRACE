# Ограниченный адаптер JSON Semgrep Code

19 октября 2026. `tools/convert_semgrep_report.py` преобразует локальный оригинальный JSON-отчёт в отдельные `trace.intake/1` файлы для очереди SAST и манифест преобразования. Не запускает Semgrep, не читает исходники/git checkout и не отправляет данные в API или внешнюю сеть. Реальное выполнение Semgrep этим этапом не подтверждается.

## Использование

Из корня trace-core, в установленном Python-окружении TRACE:

```powershell
.\.venv\Scripts\python.exe tools/convert_semgrep_report.py --report semgrep.json --source-id APPSEC_SOURCE_ID --asset-id REPOSITORY_ASSET_ID --run-id pipeline-run-123 --commit FULL_COMMIT_HEX --observed-at 2026-10-19T18:00:00Z --output-dir converted-run-123
```

Замените placeholders. Нужны ранее зарегистрированные источник appsec и актив repository, уникальный ID запуска, полный lowercase commit 40/64 hex и заявленное время наблюдения с timezone. Ни версия кода, ни время не выводятся из mtime/названия файла. Принадлежность отчёта commit пока заявляет оператор; проверка git/CI provenance не выполняется. Изменение commit в уже принятой записи с тем же externalId получает 409, а не переписывает историю.

Каталог вывода должен быть новым. После успешной записи `manifest.json` проверьте reportState, количества, исходный SHA-256 и список finding-файлов. Во вкладке SAST → «Импортировать наблюдение SAST» выберите `finding-001.json`, затем проверьте и импортируйте. Для каждого следующего finding-файла повторите действие. Можно использовать прежний подписанный intake по одному документу. Манифест и оригинальный JSON не являются intake-документами. Пакетного атомарного импорта пока нет.

Exit code 0 означает экспорт без сообщённых в сводках ошибок/пропусков; 2 — partial/unknown либо ошибка преобразования (наличие готового manifest отличает готовый экспорт от отказа). Нельзя считать 0 подтверждением покрытия или безопасности. Каталог без manifest означает незавершённый экспорт: не импортируйте его файлы. При ошибке записи ранее созданные новые файлы не удаляются автоматически. Существующий каталог/файлы никогда не перезаписываются. Для повторной доставки используйте неизменные готовые файлы.

## Контракт и ограничения

Исходный файл до 1 МиБ, не более 100 результатов. Требуются results[], errors[] и version. Слишком большой отчёт, неверная запись, точный дубль, неизвестный severity или некорректный контекст отклоняют преобразование целиком до создания каталога. Объём не обрезается. Поддерживается Semgrep Code JSON; SARIF и отчёты других продуктов не поддерживаются. Самостоятельного надёжного определения продукта по произвольному JSON нет — оператор выбирает отчёт Code, а не Secrets/Supply Chain.

Из результата берутся check_id, path, start.line, end.line, extra.severity и is_ignored. Правило/путь/строки проходят прежнюю строгую схему intake. Абсолютные, UNC/Windows, traversal пути отклоняются, преобразование в относительные по догадке не выполняется. Отчёт должен содержать пути относительно корня репозитория. Произвольные сообщения, код/lines, metavars, fix, metadata и содержимое ошибок не копируются и не выводятся в лог. Заголовок равен rule ID, описание фиксированное; это не каталог описаний правил.

CRITICAL/HIGH/MEDIUM/LOW/INFO сопоставляются одноимённым уровням TRACE. ERROR/WARNING остаются unknown в severity, исходная метка сохраняется отдельно. Это явная политика адаптера: диагностическая метка не выдаётся за высокую/среднюю опасность. is_ignored=true исключает запись из intake, но учитывается в ignoredResults манифеста. Пустой/полностью ignored отчёт не создаёт фиктивную «чистую» находку.

В analysis добавлен optional origin: adapter=semgrep-json/1, runId, commit, reportSha256, reportState, reportedSeverity. Поля входят в immutable payload и checksum. У старых записей origin не появляется; каноническая сумма остаётся прежней. Данные источника остаются not_attested. ExternalId детерминирован по runId, SHA-256 исходных байтов и индексу результата. Другой порядок/байты/запуск дают новые наблюдения; автоматической группировки occurrence между отчётами нет.

Состояния:

- partial — сообщены errors, skipped paths или skipped rules;
- no_reported_errors — errors пуст, переданы paths.scanned/paths.skipped и skipped_rules без пропусков;
- unknown — данных сводок недостаточно.

Манифест `trace.semgrep-conversion/1` содержит количества и coverageVerified=false, но не содержимое ошибок/исходников. Эти состояния не подтверждают успешное завершение процесса, exit code Semgrep или полное покрытие: адаптер читает только файл. Манифест пока локальный, в БД TRACE не регистрируется; на каждой импортированной находке остаются reportState и исходный hash. Для нулевого отчёта не создаётся серверная запись запуска.

Evidence указывает SHA-256 точных исходных байтов. Оригинальный файл не копируется/не загружается автоматически: он может содержать исходники и секреты. Прежнее ручное evidence-хранилище ограничено 64 КиБ и не подходит для любого исходного отчёта. Совпадение SHA подтверждает байты, а не достоверность анализа или его соответствие commit.

## Проверка

Шесть новых тестов покрывают преобразование/детерминизм/редакцию, политику severity, partial/unknown/ignored/empty, строгий контекст и пути/дубли/лимиты, CLI с отказом перезаписи/без вывода содержимого, API roundtrip/идемпотентность/конфликт commit и invalid origin. Общий прогон: 208 тестов, OK (341,482 с); TypeScript, production build и 7 API-client checks прошли. Все 42 таблицы рабочей БД и 13 прежних находок сохранены. Сквозная UI-проверка использует отдельную БД: CLI преобразует намеренно partial fixture, файл загружается через новую форму, карточка показывает путь/строки, commit как operator-declared, исходный ERROR без повышения риска и partial без утверждения покрытия. Semgrep при этом не запускался.

Формат полей сверялся с [официальным описанием Semgrep JSON/SARIF](https://docs.semgrep.dev/semgrep-appsec-platform/json-and-sarif). Далее — пакетный приём манифеста с журналом преобразования и результатов; проверяемая привязка к коду и отдельный executor остаются отдельными этапами.
