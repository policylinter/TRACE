# Настройки рабочих пространств и ссылки на секреты

Настройки ИИ и release policy теперь сохраняются в workspace_settings с составным ключом organization/workspace/key и внешним ключом на пространство. Чтение, изменение и ORM-проверки используют серверный контекст запроса или worker. Поля области из тела запроса не используются. Изменения доступны администратору, сопровождаются аудитом в той же транзакции; в аудит попадают только имена полей.

Совместимость: прежняя app_settings не изменяется и читается только в основном пространстве. Его действующие модели, адреса и прежний ключ сохраняются. Новое пространство начинает с rules, пустого ключа, списка моделей и адресов: настройки другой команды и общий ключ установки ему не передаются. Общие числовые параметры анализа остаются начальными значениями. Политика начинается со встроенного default_policy.

В интерфейсе указана область настроек. Поле нового открытого API-ключа заменено ссылкой `env:AI_KEY`; доступны имя переменной сервера и факт обнаружения значения в API. Эта отметка не подтверждает доступность у отдельного worker и не проверяет валидность ключа у провайдера. Проверка соединения остаётся отдельной операцией, автоматически не запускается.

## Разрешение ссылки

Для organization/workspace вычисляется SHA-256 строки `organization:workspace`; первые 16 шестнадцатеричных символов в верхнем регистре включаются в имя `TRACE_WS_<HASH>_AI_KEY`. Полное имя возвращается API после сохранения ссылки. Допустимы ссылки env:NAME, где NAME начинается с заглавной латинской буквы и содержит до 48 букв, цифр и подчёркиваний. Указывать произвольные переменные, файлы, URL и секреты другого пространства нельзя.

Оператор задаёт значение в окружении API и каждого worker и перезапускает соответствующие процессы. В БД хранится ссылка; значение разрешается при чтении настроек в исполняющем процессе. При заданной, но отсутствующей ссылке прежний ключ не используется. Пустая ссылка возвращает прежнее поведение основного пространства; она не удаляет старый ключ. Старый ключ можно явно очистить административным API через apiKey="". Новые непустые apiKey отклоняются; маска и отсутствие поля сохраняют совместимость.

При сохранении прочих настроек разрешённый ключ не копируется в workspace_settings. Ответы API возвращают только маску. Настройки source/rescan разрешаются в workspace-сессии worker при выполнении. Открытые ключи по-прежнему не допускаются в параметрах фоновых заданий. Ссылки в параметрах отдельного запуска не переопределяют настройку рабочего пространства.

## Границы этапа

Это серверный environment resolver, а не Vault/KMS: нет управления значениями секретов через UI, автоматической ротации, версионирования и проверки окружения удалённых worker. Прежние ключи в app_settings автоматически не удаляются и не шифруются; резервные копии могут их содержать. Они сохранены ради работающей установки и требуют отдельного операторского переноса. Параллельное изменение одной настройки пока имеет семантику последней записи. PostgreSQL и удалённый Celery worker в живом окружении не проверялись.

Проверено на изолированных БД: изоляция настроек и политик, сохранение legacy только в default, разные переменные для одинаковой ссылки, отсутствие значений в БД/ответах/аудите, запрет открытого ключа и некорректных ссылок, права администратора, откат при сбое аудита. Полный backend suite, TypeScript, build и API-client smoke выполняются перед обновлением основного API. На рабочей установке настройки провайдера и секреты не менялись, внешние запросы к модели не запускались.
