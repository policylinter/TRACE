# Этап 2Б.2 — повторная авторизация фонового выполнения

Реализован первый законченный подэтап 2Б.2: проверка действующих прав перед исполнением очереди и фонового rescan. Постоянная очередь остаётся следующим шагом.

## Изменения

API передаёт в доверенном контексте задания числовой user_id, автора и workspace_id. Они берутся из серверного principal, а не тела запроса. Перед доступом к исходникам оба worker-пути проверяют активность пользователя, совпадение автора, активное членство организации и текущую эффективную роль в пространстве. Нужна роль analyst или admin; прямые и командные разрешения вычисляются заново. Внутренние поля удаляются до вызова конвейера.

Фоновый rescan использует ту же проверку перед загрузкой scan и запуском конвейера. Отказ записывается как failed; failed больше не остаётся active и не блокирует повторную постановку после восстановления прав.

Локальный оператор допускается только при выключенной авторизации и отсутствии статического токена. static-admin допускается только при выключенной пользовательской авторизации и настроенном статическом токене. Неизвестный system/service автор не получает права запускать сканеры. Сервисные аккаунты по существующим scopes могут импортировать результаты, но не запускать сканеры источников.

Старые сообщения очереди без user_id при включённой авторизации отклоняются. Обновление API и worker должно быть согласованным. Схема БД не изменяется; рабочие процессы и БД не перезапускались и не мигрировались.

## Проверка и границы

Тесты используют изолированные БД и подменённые конвейеры: реальные сканеры и сторонние цели не запускаются. Проверяются успешный запуск, понижение роли, отзыв grant, отключение пользователя, отзыв членства организации, отсутствие identity, локальный/статический режимы, оба worker-пути и фоновый rescan.

Проверка выполняется непосредственно перед началом работы, а не непрерывно: уже запущенное сканирование после отзыва прав автоматически не прерывается. Истечение браузерной сессии не отменяет разрешённое задание; проверяются текущие полномочия пользователя без передачи bearer-токена в очередь. Результат отказа пока хранится в памяти/результате Celery, а не в постоянном журнале заданий.

Далее: постоянные Job/Attempt и outbox, атомарное получение задания и lease, восстановление после падения, контролируемые повторы без дублирования результатов. Затем scoped settings/secret_ref, quotas и оставшиеся ограничения БД. Дополнительные организации остаются выключены.
