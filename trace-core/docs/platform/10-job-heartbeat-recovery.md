# Этап 2Б.2: heartbeat и восстановление статуса по результату

Подэтап добавляет наблюдаемость уже начатого задания и безопасное завершение его записи после потери подтверждения от worker. Автоматического повторного сканирования нет.

## Сигнал активности

При атомарном захвате Job создаются Attempt и `scan_job_heartbeats` в одной транзакции. Поток исполнения раз в 15 секунд продлевает heartbeat на 120 секунд отдельной сессией. Это работает в локальном и Celery-пути, поскольку оба используют общий executor. Поток heartbeat останавливается при обычном завершении и при выходе через исключение, включая имитацию аварии процесса. При настоящем падении процесса сигнал просто перестаёт обновляться.

GET `/api/v1/jobs` и `/api/v1/jobs/{id}` сохраняют прежние статусы Job и дополнительно возвращают executionState, requiresReview, lastHeartbeatAt и heartbeatExpiresAt. Пока срок heartbeat не истёк, executionState=responsive. После срока — heartbeat-lost и requiresReview=true. Для старой running-записи без heartbeat — unknown. Для terminal-заданий executionState совпадает с завершённым статусом, requiresReview=false.

Потеря heartbeat означает неопределённость, а не доказанную смерть процесса: возможны пауза worker, недоступность БД или блокировка записи SQLite. Ошибка продления не убивает конвейер. Позднее успешное продление возвращает responsive. Это не fencing lease и не разрешение другому worker забрать running-задание. Часы узлов должны быть согласованы; используется Unix time, как в прежних полях Job.

## Доказательство сохранённого результата

Новая таблица `scan_job_receipts` хранит Job, Attempt, ID проверки, её итоговый статус, список движков и время сохранения. Receipt добавляется в `scan_source` непосредственно перед последним commit, вместе с итоговыми scanner_results/status/engines/SBOM. Предварительный commit внутри run_scan сам по себе не создаёт receipt. Контекст Job/Attempt передаётся внутренним параметром `_run_pipeline`, а не аргументами HTTP-запроса или Celery-сообщения.

Если финальная транзакция откатывается, receipt отсутствует вместе с откатом итоговых полей. Если она зафиксирована, но worker погиб до обновления Job, запись receipt позволяет восстановить только статус и ссылку на уже существующий результат. Статус Job completed означает завершение конвейера; scanStatus=partial/failed/completed сохраняется отдельно и не превращается в подтверждение безопасности.

## Команда оператора

В окружении с явным TRACE_DATABASE_URL:

```
python -m trace_api.recover_jobs --workspace default
python -m trace_api.recover_jobs --workspace default --reconcile JOB_ID
```

Первый вызов читает до 100 последних заданий пространства и выводит только требующие проверки; `--limit` допускает 1–1000. Это не полный обход бесконечного каталога. Второй не отправляет сообщения брокеру и не запускает движки. Он проверяет scope, статус running, отсутствие свежего heartbeat, соответствие receipt текущей попытке и доступность Scan того же пространства/организации.

Свежий heartbeat, отсутствие receipt, чужое пространство, отсутствующий Scan или некорректная попытка блокируют восстановление. Условное обновление просроченного heartbeat защищает от одновременного продления. Затем Job и Attempt завершаются одной транзакцией, приватные params очищаются, сохраняется reconciled=true. В той же транзакции добавляется PlatformAudit job.reconciled с системным автором system:job-recovery. Это не персональная идентификация оператора: команда рассчитана на доверенный административный shell с доступом к БД; отдельного HTTP endpoint восстановления нет.

Обычное завершение worker также использует условный UPDATE running. Запоздалый worker не перезаписывает уже восстановленный результат. Повтор команды не создаёт второй результат или вторую попытку. Сканер не запускается ни при одном исходе reconcile.

## Интерфейс

На странице «Проверки» добавлен реальный каталог последних 20 фоновых заданий выбранного пространства. После обновления страницы кнопка «Наблюдать» возвращает наблюдение за сохранённым Job. Завершённые задания отображают scanStatus, а не только состояние очереди. Каталог относится ко всему пространству, что указано явно; история проверок ниже по-прежнему относится к проекту.

Для heartbeat-lost показываются «Потеряна связь с worker», время последнего сигнала и объяснение неопределённости. Для legacy unknown — «Выполнение не подтверждено». Кнопка повторного запуска остаётся недоступной, пока выбранное задание running. После reconcile интерфейс подхватывает completed обычным polling и показывает основание восстановления. При пустом каталоге выводится сообщение об отсутствии заданий; ошибки загрузки не подменяются пустым списком. Старые API без новых полей сохраняют прежнее отображение.

## Миграция и проверка

Добавляются только две таблицы; старые Job/Attempt и бизнес-строки не переписываются. На отдельной копии прежней БД два последовательных init сохранили содержимое всех 21 существующей таблицы, проверенное хешами строк. Рабочий API и его БД не обновлялись. API/worker следует обновлять согласованно после backup.

Полный набор из 65 unittest прошёл. После добавления проверки запоздалого worker и атомарного аудита повторно прошли все 7 профильных тестов восстановления. Проверены продление и остановка heartbeat-потока, истечение/возобновление, legacy unknown, отсутствие receipt и результата, scope, rollback scan+receipt, восстановление без сканера и запрет перезаписи после восстановления. TypeScript, production Vite build и 7 проверок совместимости API-клиента прошли. git diff --check успешен.

Браузерная проверка выполнена на отдельном 8003 с work/heartbeat-ui.db: явно тестовые test-heartbeat-lost и test-legacy-unknown. Через живой интерфейс выбран потерянный Job, проверены предупреждение и блокировка повторного запуска. Затем отдельный процесс команды recover_jobs восстановил статус по подготовленному receipt; UI автоматически показал «Завершено частично» и основание восстановления. Это фикстуры, не результаты реального сканера. Снимки TRACE-heartbeat-lost.png и TRACE-job-recovered.png сохранены в outputs. Стенд 8003 оставлен для просмотра; основной API на 8000 и процесс 8001 не перезапускались.

## Границы и следующий подэтап

Без receipt running-задание не превращается автоматически в failed или queued. Нет автоматической отмены живого worker, переназначения lease, повтора частичных стадий и гарантии exactly-once внешних эффектов. Reconcile не восстанавливает удалённые результаты. Heartbeat не добавлен к старому фоновому rescan: его перенос в общий Job lifecycle остаётся отдельной задачей. Реальные Redis/Celery и PostgreSQL в этой итерации не использовались.

Далее: периодический outbox dispatcher с ограничением параллелизма/backpressure, явное управление отменой и квотами, retention, затем идемпотентные стадии для безопасного retry и перенос rescan. Scoped settings/secret_ref и оставшиеся ограничения БД по-прежнему нужны до включения дополнительных организаций.
