# Пакетный приём Semgrep и журнал

19 октября 2026. Реализован атомарный приём результата локального преобразования Semgrep: манифест и до 100 нормализованных наблюдений одной транзакцией. Сканер не запускается. Исходный отчёт и код не загружаются.

## Использование и совместимость

Повторите преобразование исходного отчёта обновлённым `tools/convert_semgrep_report.py` в новый каталог. Манифест теперь содержит `documentSha256` — каноническую SHA-256 каждого intake-документа в порядке files. Это сумма нормализованного JSON, не исходных байтов finding-файла. Пробелы/отступы JSON не влияют на неё. Старые манифесты без documentSha256 для пакета не подходят; прежний поштучный приём сохранён.

В SAST откройте «Пакетный импорт Semgrep и журнал приёма». Выберите одновременно manifest.json и все указанные finding-*.json из одного каталога. Клиент проверяет набор имён/размер, сервер — схему, суммы, контекст и права. До 101 файла и 1 МиБ суммарно в браузере, до 1 МиБ тела запроса на сервере. Файлы сервера не читаются по именам манифеста, произвольные URL не загружаются. Подготовка файлов в форме ничего не импортирует.

POST `/api/v1/platform/semgrep-batches` принимает `{manifest,results}`; results идут в порядке manifest.files. Источник должен быть appsec, актив — repository своего пространства. Требуются совпадающие source/asset/runId/commit/reportSHA/reportState/observedAt у всех записей, корректные суммы, уникальные externalId, последовательные имена finding-001.json… и согласованные output/input/ignored counts. Сообщённые errors/skips требуют partial, недостаточная сводка не допускает no_reported_errors. Дополнительный контекст поставки в пакетах пока не поддерживается; для него остаётся поштучный intake.

## Транзакция и повторы

Блокировка источника сериализует конкурентные импорты. Сначала проверяется весь пакет, затем каждый результат проходит общий ingest_result(commit=False). Payload, primary intake receipts, аудит результатов, журнал пакета и аудит пакета коммитятся вместе. Конфликт даже последней находки или сбой аудита откатывает всю транзакцию, включая ранее подготовленные новые находки и receipt.

Точная повторная отправка одного sourceId/runId возвращает 200 и прежнюю запись без новых находок/receipt/аудита. Иной пакет с тем же sourceId/runId — 409 (если он сам проходит проверку схемы/сумм). Изменённый файл с прежней суммой — 422. Уже отдельно принятый идентичный результат используется повторно, а не дублируется; createdCount/reusedCount фиксируют первоначальный приём. Историческая точная доставка допускается и после отключения источника, новые пакеты в выключенный источник запрещены.

Пустой пакет тоже требует действительных source/repository и контекста, но создаёт только receipt доставки с resultIds=[], без находки и без подтверждения безопасности. Нельзя считать пустой список или no_reported_errors доказательством покрытия.

## Журнал и права

Добавлена таблица semgrep_batches с Unique(source_id,run_id), org/workspace scope, привязками source/repository, канонической суммой пакета, исходным манифестом, ID результатов, счётчиками созданных/повторно использованных результатов и серверными автором/временем. ORM запрещает изменение/удаление журнала, в том числе bulk; проверяет область и привязки результатов к источнику/активу. Это ограничения обычной БД, не WORM-хранилище или подпись независимой стороны.

GET того же пути возвращает scoped журнал (UI по 20 записей, API до 100 с offset), от новых к старым. Читать могут прежние read-роли, импортировать — admin. Сервисным аккаунтам новые полномочия не выдаются. Неуспешные запросы не сохраняются в этом журнале: отклонённая транзакция не оставляет успешного receipt. Внешний immutable audit sink, журнал ошибок доставки и расписания — не часть этапа.

Суммы обеспечивают согласованность файлов и принятого пакета. Они не удостоверяют достоверность исходного Semgrep-отчёта или соответствие указанному commit; эти поля по-прежнему operator-declared/not_attested. Сервер не получает исходный отчёт и не пересчитывает reportSHA по нему. Клиент/оператор может подготовить согласованные значения; независимой аттестации не заявляется.

## Проверка и следующий шаг

Семь новых API-тестов: атомарный приём/повтор/конфликт, откат при конфликте второй находки с сохранением прежнего аудита, суммы/контекст/counts/границы тела, роли/изоляция/отключение, одновременные запросы, нулевой пакет без фиктивных находок, сбой финального аудита и защита ORM. Общий набор: 215 тестов, OK (348,011 с); TypeScript/build и 7 API-client checks прошли.

В браузере на отдельной QA-базе выбраны три файла (манифест и две находки), принят пакет: создана одна находка и использована одна ранее принятая. Повторное нажатие сохраняет две находки и одну запись журнала, карточка показывает автора, время, partial, SHA пакета/отчёта и ID результатов. Тестовые данные не добавлялись в рабочую установку: все прежние 42 таблицы совпадают с резервной копией, новый рабочий журнал пуст, 13 legacy-находок проверены через 5173. Предварительно init_db дважды проверен на копии БД с сохранением старых строк.

Далее — отдельное управляемое выполнение SAST и привязка к проверяемой версии кода. Пакетный приём не означает, что Semgrep установлен или выполнялся, CI pipeline подключён либо уязвимость независимо подтверждена.
