# Этап 2Б.1 — рабочие пространства и команды

17 октября 2026. Реализована изоляция рабочих пространств внутри одной организации. Это законченный вертикальный сценарий следующего подэтапа; весь этап 2Б и поддержка нескольких организаций ещё не завершены.

## Рабочий результат

* Workspace отделён от Project: пространство содержит проекты, активы, проверки, находки, связи и историю. Все прежние записи получают workspace_id=default, имена и ID не меняются. Новое пространство начинается пустым, без демонстрационных проверок и фиктивных показателей.
* Team, TeamMember, WorkspaceMember и WorkspaceTeam хранят командные и прямые разрешения. Создание команды само по себе не выдаёт доступ. Администратор организации управляет пространствами, составом команд и grants; остальные видят только пространства, к которым имеют доступ.
* Для участника эффективная роль — максимум активных прямых и командных разрешений, ограниченный сверху ролью организации. Например, аналитик организации с командной ролью viewer в пространстве читает данные, но не меняет их. Наблюдатель организации не становится аналитиком из-за более сильного grant. Администратор организации по назначению видит все её пространства.
* Отзыв team membership, прямого grant или разрешения команды применяется при следующем запросе. Отзыв одного источника доступа не отменяет другой. Отключённым участникам можно отозвать оставшиеся старые grants; миграция не восстанавливает отключённый доступ.
* В верхней панели появился переключатель пространства и раздел «Пространства и команды». Создание пространств и команд, состав команды, прямые и командные grants, отзыв — реальные API-операции с аудитом.

## Контекст API и данных

X-Trace-Workspace выбирает пространство; без заголовка используется default для совместимости. Поле в теле объекта не назначает scope. Сервер проверяет членство и текущие grants, затем привязывает Session к organization_id и workspace_id. Заголовок X-Trace-Organization с другой организацией по-прежнему запрещён.

OrganizationSession фильтрует ORM SELECT, relationship loaders, count/join и bulk DELETE/UPDATE. Запись проверяет ownership и ссылки Project → Scan → Finding, Asset → Project и AssetLink → Asset. Bulk UPDATE не может менять scope или ссылки в обход этих проверок. Обращение к чужому известному ID возвращает 404 в доступном пространстве; попытка выбрать недоступное пространство — 403. Проверены списки, детали, advisory joins, события, health counts, SBOM, VEX, compliance, findings, progress и начало async rescan.

Новые таблицы grants имеют составные FK по organization_id и родительскому Workspace/Team. Legacy бизнес-таблицы расширяются полями scope, а согласованность их старых связей проверяется приложением. Это **не** PostgreSQL RLS и не защита от доверенного оператора с прямым SQL-доступом. Старые бизнес-таблицы ещё не все получили составные FK — одна из причин не включать второй tenant.

API:

| Маршрут | Назначение |
|---|---|
| GET /api/v1/workspaces | Только доступные пользователю пространства и эффективные роли; discovery не требует доступа к ранее сохранённому выбору |
| POST /api/v1/workspaces | Создать пространство, администратор организации |
| GET /api/v1/workspaces/{id}/grants | Прямые и командные grants, администратор |
| PUT /api/v1/workspaces/{id}/members/{userId} | Назначить/изменить/отозвать прямой grant |
| GET/POST /api/v1/teams | Каталог/создание команд, администратор |
| GET/PUT /api/v1/teams/{id}/members[/{userId}] | Состав команды и включение/исключение участника |
| PUT /api/v1/workspaces/{id}/teams/{teamId} | Назначить/отозвать роль команды в пространстве |

Членство в организации и права её администратора остаются общими для организации. Журнал платформы /access/audit показывает записи выбранного пространства; изменения команд/grants записываются в контексте, из которого их выполнил администратор.

## Сервисные аккаунты и задания

Сервисный аккаунт привязан к одному workspace_id при выдаче. Старые credentials привязаны к default. Для другого пространства клиент должен явно передать соответствующий X-Trace-Workspace; подмена заголовка на соседнее пространство запрещена. Импорт принимает только projectId того же пространства. Каталог аккаунтов и их отзыв также учитывают выбранный контекст; scopes и срок действия сохраняются. Создание дополнительных service credentials через браузер при проверке не выполнялось.

Диспетчер передаёт серверный _workspace_id вместе с автором в поток или Celery. Общий _prepare_execution восстанавливает Session, проверяет пространство и принадлежность проекта **до** fetch исходников и запуска движков, затем убирает внутренние поля из аргументов конвейера. Статус/список заданий фильтруется по workspaceId до обращения к broker backend. Async rescan сохраняет scope и сначала проверяет доступный scan. В тестах проверены оба пути исполнения без реальных сканеров и брокера.

Очередь пока не стала постоянной: реестр API-заданий всё ещё живёт в памяти, нет lease/retry/outbox и автоматической отмены уже поставленных задач при последующем отзыве прав. Scope снимка разрешённого задания сохраняется; durable jobs и повторная проверка разрешений перед выполнением — следующий подэтап.

## Миграция и ключи активов

Добавлены пять таблиц Workspace/Team/grants и workspace_id в семь доменных таблиц и ServiceAccount. После старого init выполняется идемпотентное создание default-пространства. Существующие участники один раз получают default-grant с совместимой ролью; marker access.legacy-workspace-grants.v1 предотвращает его восстановление после отзыва. Локальная команда manage_user выдаёт новому участнику default-grant явно.

Внешний ключ актива теперь уникален по (organization_id, workspace_id, external_key). Это позволяет, например, иметь service:payments в двух пространствах. UUID/ID активов остаются глобально уникальными, поэтому старые ссылки сохраняются.

SQLite не умеет просто удалить старый UNIQUE(external_key), поэтому миграция пересоздаёт таблицу внутри явного BEGIN IMMEDIATE. Сохраняются все её обычные столбцы, ID, строки, пользовательские индексы и триггеры; ссылки не перенумеровываются. Проверяется число строк и foreign_key_check для активов и связей. Значение PRAGMA foreign_keys восстанавливается в finally. Ошибка на середине rebuild откатывает исходную таблицу вместе с данными; отдельный тест внедряет такую ошибку. Неизвестная форма legacy SQL прерывает миграцию вместо рискованной догадки. Для PostgreSQL предусмотрено транзакционное изменение constraint, но реальный прогон PostgreSQL здесь не выполнялся.

Применять обновление нужно согласованно: остановить старые API/worker, сделать backup, проверить копию, затем запустить API/worker одной версии. Старый API без workspace-фильтров нельзя оставлять с той же БД после появления новых пространств. Рабочий экземпляр на 8000 и его БД в этой работе не обновлялись.

## Интерфейс и безопасное переключение

При смене пространства очищаются проект, scan, выбранная находка, сравнение, уведомления и формы. В корне React меняется ключ всего TraceProvider: запоздалые ответы предыдущего пространства не записываются в новое состояние. Scope хранится в памяти вкладки; localStorage сохраняет только последний выбор для следующего открытия и не переключает незаметно запросы другой вкладки. Ссылки на находки содержат workspace вместе со scan/finding.

Если сохранённое пространство недоступно, каталог позволяет выбрать первое доступное; при отсутствии grants UI сообщает об отсутствии назначенных пространств. Это не подтверждение работоспособности отсутствующих модулей и не «нулевой риск». В режиме AUTH_ENABLED=0 личные ограничения не действуют, что явно написано на странице; разделение данных по выбранному контексту сохраняется.

## Проверка результата

* 47 unittest: прежние 35 регрессий и 12 новых сценариев. Включены team/direct grants, отзыв и потолок роли, чужие IDs/экспорты/списки, bulk ownership, смешанные ссылки, service binding, статус задания, оба worker-пути, запрет смешанного project scope до сканирования, поведение неактивных участников, уникальность ключей и миграции.
* SQLite-тест rebuild выполняется с включёнными FK, дополнительным столбцом, пользовательским индексом и триггером. Проверены идемпотентность, сохранность ссылок и rollback при внедрённой ошибке.
* На отдельной копии прежней work/ui-test.db init выполнен дважды: сохранены 2 старых актива, 1 связь, исходные ID, имена и ключи. Резервная копия: work/ui-test-before-workspaces.db. После этого обновлён собственный тестовый стенд 8001.
* Ещё 7 проверок реального API-клиента проходят через `node scripts/api-compat-smoke.mjs` (`npm run test:api`): только 404 каталога включает legacy-режим; 401/403/500 не маскируются; успешный ответ сохраняется; выбор другой вкладки не меняет scope текущего запроса.
* TypeScript и production Vite build успешны. Использован тот же проверенный программный запуск Vite с configFile:false из-за ограничений esbuild CLI в этой среде. Основной vite.config.ts не менялся.
* В браузере 8001 созданы явно тестовые пространство и команда, проверены переключение, пустой новый реестр, регистрация актива с тем же test:service, что в default, и возврат к двум прежним активам. Тестовые записи остаются в отдельной БД стенда.
* На 8002 использовалась отдельная копия с обязательным входом и тестовыми учётными записями. Аналитик видит default с ролью аналитика и «Тест: приложения» с командной ролью наблюдателя; «Тест: инфраструктура» ему не показывается. В командном пространстве форма изменения активов отсутствует. Права настроены только тестовыми fixtures/API-тестами; браузерная проверка читала их. После QA стенд 8002 остановлен.

## Совместимость с основным интерфейсом на 5173

Основной API на 8000 пока возвращает 404 для /workspaces и не перезапускался. Поэтому новый API-клиент распознаёт только этот 404 как старую версию: сохраняет прежнюю загрузку проектов, проверок и находок в явно обозначенном «Контексте установки». Это служебный descriptor с legacy=true, не фиктивная запись Workspace и не подтверждение изоляции на старом сервере.

Новые страницы активов, доступа, пространств и команд в legacy-режиме показывают «API платформы ещё не обновлён», а не формы с неработающими операциями. 401/403/500 не переводят приложение в открытый режим и не обходят серверную авторизацию. Подтверждена загрузка прежнего проекта и сохранённых результатов через браузер на 5173, затем проверена надпись об обновлении API для нового раздела. В рабочую БД тестовые записи не добавлялись.

Для всех новых возможностей в основном экземпляре нужно согласованно обновить API/worker с проверенной миграцией. Полностью работающий отдельный стенд — 8001; его прежние и новые явно тестовые записи находятся в work/ui-test.db.

## Ограничения и следующий подэтап

2Б.2: постоянные Job/Attempt/outbox, повторная проверка прав перед исполнением, расписания, quotas, настройки и secret_ref для организации/пространства, остальные составные FK и тестирование PostgreSQL. Затем — возможность второй организации. Полноценная SIEM, IAM/PAM/DLP и другие направления остаются по матрице возможностей.

Пока нет переноса/архивирования существующих ресурсов и удаления пространств/команд, кастомных ролей, SSO/MFA, постоянной очереди, tenant-specific secret store и общего обзора организации поверх нескольких пространств. Каталоги пространств/команд рассчитаны на небольшой текущий проект и ещё не имеют cursor pagination; масштаб и retention нужно проверить до промышленных обещаний.
