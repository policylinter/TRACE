# Сравнение снимков инфраструктурной инвентаризации

Добавлено read-only сравнение двух выбранных снимков одного источника. Оно показывает различия в сохранённых сведениях; не запускает сбор, не меняет реестр, ответственных или историю наблюдений, не удаляет активы и не создаёт уязвимости.

## API и правила

`GET /api/v1/platform/inventory/sources/{source_id}/compare?before=RUN_ID&after=RUN_ID&includeUnchanged=false&offset=0&limit=50`

Оба снимка должны принадлежать указанному источнику и текущему пространству. Неизвестные/чужие записи — 404. before должен быть строго раньше after; одинаковые ID и обратный порядок — 422. Сравниваются конкретные неизменяемые ID, поэтому новый импорт не меняет уже выбранную пару. Снимки не обязаны быть соседними.

Перед сравнением проверяются контракт trace.inventory/1, SHA-256 исходного payload, externalRunId и время против метаданных сохранённой записи. При нарушении целостности возвращается status=unavailable/reason=integrity_error. Если любой из корректных снимков сообщает status=error, результат unavailable/collection_error. В обоих случаях counts=null и items пуст: неудачное сравнение не показывается как «ноль изменений».

Идентичность узла — точный externalId внутри источника. Порядок items не учитывается. Сравниваются name, kind, заявленный owner, platform, version, provider и region. Для изменившегося узла возвращаются только реально отличающиеся поля с before/after. Это сведения источника, а не автоматические изменения назначения владельца в реестре.

Категории:

- only_after — узел есть только в новом из выбранных снимков; это не доказательство первого появления в инфраструктуре;
- changed — отличаются сведения общего узла;
- not_in_after — узел отсутствует в новом снимке, который отправитель обозначил complete; это не подтверждение удаления;
- not_observed_partial — узел не попал в новый partial-снимок; оснований считать его отсутствующим нет;
- unchanged — выбранные сведения совпали.

Статус complete относится только к заявленной области конкретного снимка. Принадлежность одному источнику не является независимой гарантией одинакового охвата двух сборов. Отсутствие и новые узлы трактуются только в границах выбранной пары, без автоматических lifecycle-решений. При частичном базовом снимке отсутствие узла в нём также не означает, что узел действительно новый.

Ответ trace.inventory-comparison/1 содержит идентификаторы/суммы/время/статусы обоих снимков, время расчёта, счётчики всех категорий и ограниченную страницу элементов. Максимум 100 элементов на страницу; union двух снимков ограничен контрактом импорта (до 200 идентичностей). По умолчанию unchanged скрыты в списке, но входят в счётчик. Порядок — externalId; пагинация стабильна для выбранной пары. Ссылка assetId берётся из существующей привязки источника, новые активы при просмотре не создаются.

## UI и права

В блоке инвентаризации добавлено «Сравнение снимков»: выбор базового/нового снимка из 10 последних, переключатель узлов без изменений, счётчики, карточки before → after и переход к общему активу. Выбранные снимки сохраняются при поступлении новых импортов; выбранный старый ID остаётся доступен в списке. API поддерживает любые известные ID источника, UI ограничен недавней историей и закреплённой парой. Ошибка сбора, частичный охват и невозможность сравнения обозначаются явно.

Чтение доступно admin/analyst/viewer своего пространства. Права сервисных аккаунтов не расширены. Источник может быть выключен для новых импортов: его исторические снимки остаются доступными. GET не пишет аудит или историю и не принимает решений о списании.

## Проверка и границы

Пройдены 178 тестов общего набора, TypeScript, сборка и 7 проверок API-клиента. Добавлены 8 тестов: категории полного сравнения и поля изменений, частичный/ошибочный сбор, частичная база/пустой полный снимок, стабильная пагинация/порядок, отсутствие побочных записей, роли/изоляция/чужой источник, повреждённый payload, независимость от порядка узлов и новых импортов. В отдельной базе через UI проверены отказ от выводов по error-снимку, полное сравнение и перевод отсутствующего узла в категорию not_observed_partial для частичного сбора. После дополнительного импорта через UI также проверено сохранение выбранной пары. Активы сохранены; тестовые записи в рабочую БД не добавлены.

Новых таблиц и изменения формата сохранённых снимков нет. Это вычисление различий, не автоматический drift alert, аттестация охвата или доказательство уязвимости. Автоматическая корреляция разных источников, расписания, подтверждение удаления и workflow согласования изменений остаются отдельными этапами. Следующий этап — управляемая сверка отсутствующих узлов с причинами и историей решений без автоматического удаления.
