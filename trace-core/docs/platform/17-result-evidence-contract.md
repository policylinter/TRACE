# Контракт результата и доказательств: первый адаптер

Добавлен версионированный контракт `trace.result/1` и read-only адаптер `legacy-appsec/1` для существующих AppSec Finding. GET `/api/v1/findings/{id}/result` возвращает тип finding, модуль, область, связь с проверкой и проектом, координаты пакета, текущее состояние, сообщённую уверенность и отдельные записи доказательств. JSON Schema доступна в OpenAPI через response model FindingResult.

Это проекция текущей записи, без миграции находок, новой дедупликации и запуска анализа. SecurityEvent, Detection, Investigation, Incident и Risk не создаются из Finding автоматически. Для них нужны собственные адаптеры и жизненные циклы, а не смена названия поля objectType.

## Семантика

Три категории сохраняются раздельно:

- reported_observation — контекст исходного отчёта, frames, dependencyPath, usage, reachability и blocker. Это сообщённые данные, а не удостоверенное наблюдение runtime.
- engine_assessment — headline, reasoning, deepAnalysis, remediation и сведения о модели. Источник rules/model принимается только из явно сохранённого deepAnalysis.source; иначе unknown. Наличие имени модели само по себе не доказывает её запуск.
- team_decision — текущие reviewed, workflow status, ответственный, срок, комментарий и причина исключения. Это снимок состояния, не полная история решений и не подтверждение исправления.

У всех записей verification=not_attested и observedAt=null: прежняя модель не содержит независимого удостоверения происхождения или времени наблюдения. Время записи находки и время проверки возвращаются отдельно и не выдаются за collected_at. Naive даты прежней SQLite интерпретируются как UTC, как и прежние записи приложения. Уверенность возвращается только конечным числом от 0 до 1, иначе null; она не определяет подтверждённость. Демо отмечается по идентификатору встроенной демонстрационной проверки, а не по содержимому отчёта.

Идентичность основана на прежнем findingId. Стабильный fingerprint/occurrence между разными проверками пока не вводится: недостаточно удостоверенной связи с артефактом. Разные версии пакетов не объединяются.

Каждый payload и весь нормализованный ответ имеют SHA-256 от UTF-8 JSON с отсортированными ключами, без пробелов и с буквальными Unicode символами. Поле snapshotSha256 исключается из собственного хеша; время формирования ответа не добавляется. Эти хеши позволяют сравнить содержимое, но не доказывают источник, подпись, неизменность БД или истинность утверждения. Формат сериализации v1 зафиксирован для Python JSON; межъязыковая JCS-канонизация не заявляется.

## Интерфейс и доступ

В полной карточке находки доступен раскрываемый блок «Происхождение результата и доказательств»: категории, источники, контрольные суммы, ограничения и скачивание нормализованного JSON. Запрос выполняется при открытии блока; ошибка видна с кнопкой повтора. Данные обновляются после изменения находки. Старые поля карточки, обработка и анализ продолжают работать.

Права совпадают с чтением находок: пользователь с доступом к пространству, включая наблюдателя; сервисный аккаунт только с findings:read в своём пространстве. inventory:read недостаточно. Чужой или отсутствующий findingId возвращает 404, не создаёт демо и не запускает работу. GET не пишет находки, аудит или события. Операции создания/редактирования этим маршрутом не предоставляются.

## Проверка и границы

Шесть новых интеграционных тестов проверяют детерминированность и хеши, отсутствие записей при чтении, изоляцию и права, раздельные категории, отсутствие ложной аттестации и изменение снимка при изменении workflow. Сборка frontend, TypeScript и 7 проверок клиента API проходят. Полный backend suite выполняется перед обновлением API.

Следующие этапы: контракт приёма результатов с идемпотентностью и валидируемой ссылкой на источник, occurrence/fingerprint с доказанной идентичностью артефакта, evidence storage и аттестация с актором/методом/временем. Вебхуки, поток событий SIEM и активное реагирование этим изменением не включаются.
