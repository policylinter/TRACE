# Файлы доказательств импортированных результатов

Добавлено ограниченное хранение исходных байтов доказательства для существующего `trace.intake/1`. Раньше запись содержала только label/reference/sha256, сообщённые отправителем. Теперь analyst/admin может загрузить соответствующий небольшой файл, а сервер независимо вычислит SHA-256 и сравнит его с неизменяемым отчётом. Совпадение подтверждает соответствие байтов заявленной сумме, но не достоверность наблюдения, аттестацию инструмента или исправление проблемы.

## API и интерфейс

- `GET /api/v1/platform/module-results/{result_id}/evidence`: до 20 ссылок из исходного отчёта, состояние not_stored / hash_matches / integrity_error, размер, время и автор загрузки. Хеш байтов пересчитывается при чтении состояния.
- `PUT /api/v1/platform/module-results/{result_id}/evidence/{index}`: сырой файл, Content-Type application/octet-stream. Индекс от 0 до 19 должен существовать в исходном отчёте. Лимит 65536 байт проверяется при чтении потока до накопления превышающего лимит тела. Неверная сумма — 422; превышение — 413; другой тип тела — 415.
- `GET /api/v1/platform/module-results/{result_id}/evidence/{index}/content`: повторная проверка целостности перед скачиванием; ошибка — 409, отсутствующий файл — 404. Выдача только application/octet-stream, attachment с фиксированным именем .bin, nosniff, CSP sandbox и no-store. Пользовательские имена не попадают в HTTP-заголовки.

В раскрытой карточке импортированного результата есть раздел «Файлы доказательств». Для каждой ссылки показаны ожидаемый SHA-256 и факт наличия файла. До отправки браузер проверяет размер и SHA-256, сервер повторяет проверку независимо. После сохранения форма заменяется кнопкой скачивания. Есть повторная проверка целостности. Файл не отображается в HTML-предпросмотре.

## Неизменяемость и область доступа

`module_result_evidence` содержит составной ключ result_id/evidence_index, organization/workspace, bytes, SHA-256, byte_count, stored_at, stored_by. Файл и запись аудита коммитятся одной транзакцией; сбой аудита откатывает загрузку. Сериализация по источнику предотвращает гонку первых загрузок. Повтор тех же байтов возвращает прежнюю запись (200 вместо 201) без повторного аудита. Повреждённую копию нельзя заменить этим API; состояние явно помечается ошибкой, скачивание блокируется.

ORM ограничивает чтение пространством, проверяет ссылку на результат и запрещает изменение/удаление записей, включая bulk операции. Viewer читает и скачивает; analyst/admin загружает. Сервисные аккаунты и ключ подписанного CI intake права на файлы не получают. Отключение новых импортов источника не мешает обработке уже принятых отчётов. Внешние URL/reference автоматически не открываются и не загружаются.

Исходный payload, его контрольная сумма, контекст поставки, workflow и история решений не переписываются. Старым отчётам ничего не приписывается: до загрузки соответствующих байтов они показывают «Файл не загружен». Для новой версии доказательства нужен новый отчёт с новой суммой. Демонстрационные AppSec-находки legacy adapter остаются прежними.

## Проверки и границы

Пройдены 152 теста общего набора, TypeScript, сборка и 7 проверок API-клиента. Восемь новых тестов проверяют roundtrip произвольных байтов, роли/сервисные аккаунты, изоляцию, неверную сумму/индекс/тип тела, размер/пустой файл, конкурентную дедупликацию, откат аудита, неизменяемость и повреждение данных. Через браузер в отдельной базе выбран и загружен тестовый файл, получено состояние hash_matches; скачанный через UI файл побайтово совпал с оригиналом. Рабочая база не заполнялась тестовыми отчётами и файлами.

Это хранение небольших доказательств в БД: максимум 20 × 64 КиБ на один отчёт. Большие файлы, object storage, шифрование через KMS, автоматический retention/общая квота, потоковая выдача крупных объектов и асимметричная аттестация не реализованы. Сумма не является независимым свидетельством истинности отчёта. Подписанный CI пока передаёт ссылки/суммы; отдельной машинной загрузки файлов для него нет. Проверено на локальной SQLite-установке; промышленный масштаб и PostgreSQL здесь не заявляются проверенными.

Следующий этап — проверяемое происхождение отчёта: связать зарегистрированный способ доставки, журнал CI и сохранённые доказательства в понятную цепочку без автоматического присвоения статуса «Подтверждено».
